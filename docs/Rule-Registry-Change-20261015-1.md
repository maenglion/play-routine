## 1. 확정 구조

**Quest는 수치 조건을 판정하고, 데일리는 매일 수행을 스티커로 기록한 뒤 기간별 스티커 구간을 판정한다. 각 보상 조건에는 보상 1개 또는 2개를 설정할 수 있으며 두 번째는 필수가 아니다.**

| 구분 | 측정하는 것 | 보상을 판단하는 기준 | 보상 연결 |
| --- | --- | --- | --- |
| Quest | 점수·퍼센트 등 수치 | 해당 Quest의 조건/구간 | 조건별 보상 1개 또는 2개, 두 번째 선택 |
| 데일리 | 오늘 했다/안 했다의 부모 확인, 활동별 PASS 스티커 | 정해진 기간에 모은 스티커 수의 기본·추가 구간 | 구간별 보상 설정, 높은 구간 달성 시 등록한 추가 리워드 |

같은 조건에 두 보상을 붙이는 것과, 더 높은 조건에 추가 보상을 붙이는 것은 **서로 다른 관계**다.

```text
활동/룰
  ├─ 조건 또는 달성 구간 A
  │    ├─ 보상 1
  │    └─ 보상 2 (선택)
  └─ 추가 조건 또는 달성 구간 B (선택)
       ├─ 추가 보상 1
       └─ 추가 보상 2 (선택)
```

보상 관계는 조건별 1:N 구조로 만들되 등록·게시 검증에서 최대 2개로 제한한다. 두 슬롯을 모두 채우도록 강제하지 않는다. 미완성 임시저장은 0개도 가능하고, 중립·미달·hold에는 보상 없음 상태가 별도로 존재한다. 보상 조건을 게시할 때에는 선택한 보상 항목을 검증한다.

## 2. Quest — 수치 조건별 보상

사용자 예시:

```text
Quest: 시험 결과
조건: 부모가 확인한 점수 > 90
  ├─ 현금: 부모가 입력한 금액
  └─ 시간: 120분 (두 번째 보상을 선택한 경우)
```

현금만 설정해도 유효하고, 시간만 설정해도 유효하다. 두 가지를 설정했다면 **동시에 받을 보상**이며 아이가 둘 중 하나를 고르는 선택권이 아니다.

Quest를 두 개 복제할 필요는 없다. 하나의 Quest 조건에 두 보상 항목을 연결하고, 같은 부모 확인을 근거로 각각 보상 권리를 기록한다. 실제 현금 지급과 시간 사용은 독립 상태다.

기존 수치 판정의 하한·중립·보상 구간은 유지한다. 필요할 때 추가 달성 조건을 설정한다. 보상 종류가 늘었다고 수치 구간이나 활동을 중복 생성하지 않는다.

`90점 초과(>90)`와 `90점 이상(>=90)`은 구별한다. 원문의 시험 예시는 >90이며, 기존 이상 규칙을 일괄 변경하지 않는다. 문서의 ‘퍼센트·백분율’ 표현은 둘 다 수치 측정 범주로 해석하며 실제 입력은 측정 이름과 기준을 명시한다.

## 3. 데일리 — 하루 기록과 기간 보상 분리

데일리의 하루 측정은 점수제가 아니다.

| 부모가 확인한 하루 | 기본 스티커 | 칭찬 추가 스티커 | 처리 |
| --- | --- | --- | --- |
| 했다 / 문제없는 PASS | 1 | 0 | 해당 활동·수행일에 기본 스티커 |
| PASS + 선생님 칭찬 | 1 | 1 | 원문대로 같은 날 해당 활동에 추가 1개 |
| 안 했다 / 문제 있음 | 0 | 0 | 미달, 스티커 회수·자동 패널티 없음 |
| 부모 확인 전 | 미확정 | 미확정 | hold, 0개 확정과 다름 |

하루의 스티커 기록과 일·주·월·특별 이벤트 기간의 보상 판단을 별도로 둔다. 매일 스티커를 받았다는 이유만으로 기간 보상을 매일 지급하지 않는다.

예시 — 주간 기본 기준 5개, 추가 3개:

```text
이번 주 PASS 스티커 합계
  0~4개: 기본 보상 기준 미달
  5~7개: 기본 리워드 달성
  8개 이상: 기본 리워드 + 등록한 추가 리워드
```

여기서 추가 3개는 **기본 5개보다 3개 더, 총 8개**다. 위 개수는 문서 예시이며 모든 활동의 고정값이 아니다. 부모가 구간·기간·보상을 설정한다.

데일리의 추가 리워드가 존재하는 경우 상위 달성은 기본 리워드를 대체하는 것이 아니라 추가로 붙는다. 추가 구간 자체는 선택사항이다. 어느 구간도 두 보상을 필수로 요구하지 않는다.

화면에서는 현재 스티커 합계, 기본 기준, 다음 추가 기준과 연결된 보상을 보여준다. 구간이 올라가도 같은 기간의 기본 보상을 반복 발행하지 않는다.

**스티커는 달성 증거이며 보상 교환 때 소비해 0으로 만드는 자산이 아니다.** 5개 보상을 받았어도 누적 8개 판정에 같은 기간의 합계를 쓴다. 집계 대상으로 정한 스티커만 합산하며, 다른 활동의 스티커를 무조건 섞는 전역 합계는 만들지 않는다. 기본은 활동별 집계이고 묶음 집계는 대상 관계를 명시한 경우에만 지원하는 방향이다.

## 4. 단계별 등록 UI

### 1단계 — 활동·측정

활동 유형을 **데일리 / Quest**로 구분한다. 이것은 공부·생활습관·기타 같은 내용 분류와 별개다.

입력은 활동 이름, 분류, 아이 표시 키워드, 부모의 상세 확인기준이다. 데일리는 PASS 스티커와 도장 아이콘을 선택하고, Quest는 수치 측정과 단위·기준을 입력한다.

아이 키워드는 상세 확인기준과 별도 필드로 둔다. 20바이트보다는 **표시 글자 20자** 제한을 권고한다. `선생님 지적없는 하루`는 11글자지만 UTF-8 29바이트이므로 20바이트는 원문 예시를 수용하지 못한다.

### 2단계 — 조건/구간·보상

| 버튼/입력 | 역할 |
| --- | --- |
| Quest 달성조건 | 점수·퍼센트 등 해당 조건 입력 |
| 데일리 기간·스티커 구간 | 주간 5개·누적 8개 등 기간 누적 조건 입력 |
| 보상 1 | 강화물 선택과 값 입력 |
| `+ 두 번째 보상` | 같은 조건에 보상 1개 추가, 선택사항, 최대 2개 |
| `+ 추가 달성조건/구간` | 더 높은 기준에 별도 추가 리워드 설정, 선택사항 |

두 번째 보상은 제거할 수 있어야 하고 숨겨진 필수값 검증도 없어야 한다. 데일리 스티커 조건의 측정 항목은 PASS 스티커로 고정한다. 추가 3개 입력 시 총 8개를 함께 표시한다.

### 3단계 — 검토·게시

각 단계의 **임시저장 → 아래 초안 목록 → 나중에 이어쓰기**를 지원한다. 1단계만 입력하고 보상 항목이 없어도 저장할 수 있다. 게시할 때만 완성도를 검증한다.

게시본은 불변, 변경은 새 버전. 가족 시간대 기준 내일부터 효력, 오늘/과거 기록 불변을 유지한다. 기존 배정은 새 등록만으로 자동 교체하지 않는다. 임시저장·카탈로그 등록만으로 지급이 발생하지 않는다.

## 5. 보상·패널티·강화물 메뉴

메뉴는 `보상(Reward)` / `패널티(Penalty)` / `강화물(Reinforcers)`로 둔다. `Panalty` 오탈자는 `Penalty`로 고친다. 강화물은 영어 단수 `reinforcer`, 목록 메뉴 복수 `Reinforcers`다.

| 강화물 값의 종류 | 의미 | 입력·기록 |
| --- | --- | --- |
| `WON` | 원화 돈 | 부모 입력 금액, 지급 권리와 실제 지급 분리 |
| `MIN` | 시간 | 분 단위, 예정·사용 권리·실제 사용 분리 |
| `POINT` | 특정 서비스 포인트·쇼핑머니 | 서비스/단위별 독립, 다른 포인트와 합산하지 않음 |
| `STRING` | 소원·체험 | 부모가 약속한 내용과 이행 상태 |

강화물의 이름과 값 타입을 분리한다. 쿠페이머니도 이름으로 단위를 자동 추정하지 않고 부모가 타입을 선택한다. 외부 결제·충전·자동 송금은 이번 범위가 아니다.

PASS 스티커에는 미달 회수가 없으므로 스티커 차감 패널티를 만들지 않는다. 기존 Quest 수치 규칙의 명시 패널티는 유지하고, 미확인을 패널티로 바꾸지 않는다. 약 복용은 평가·보상 관계에서 계속 제외한다.

## 6. DB 관계와 운영 방어

논리 모델:

```text
활동/룰 버전
  ├─ 활동 유형: DAILY / QUEST
  ├─ 측정 방식
  └─ 조건/구간
       └─ 보상 항목 1~2개

Quest 수행건 / 데일리 기간 스티커 근거
  → 부모 확인·달성 인정
      → 선택한 보상 권리 각각 생성
          → 실제 지급/사용 각각 확인
```

데일리는 실제 수행일의 스티커 사건과 기간별 합계를 보존한다. Quest는 대상 수행건의 수치 확인을 보존한다. 두 방식은 공통 보상 항목 모델을 사용하되 같은 집계 엔진으로 억지 통합하지 않는다.

중복 방지 기준은 **자녀 + 룰 버전 + 수행건/기간 + 조건/구간 + 보상 항목**이다. 해당 조건에 보상 두 개가 설정됐다면 같은 트랜잭션에서 두 권리를 만들고, 하나만 설정됐다면 그 하나만 만든다. 미설정 두 번째 권리를 생성하거나 요구하지 않는다.

동일 요청 재전송·부모 재확인·스티커 합계 상승에 따른 기본 보상 중복 생성은 차단한다. 현금 지급 완료가 시간 사용 완료를 뜻하지 않는다. 상위 ‘돈 총액’과 ‘추가 돈’을 구별해야 하며 이미 지급된 기본 금액을 다시 지급하지 않는다.

늦은 확인은 실제 수행일의 기간에 귀속하고 기록/확인 시각을 별도로 남긴다. 이미 지급한 돈·사용한 시간을 정정으로 자동 회수하지 않는다. 자유 특별보너스는 별도 출처로 유지한다.

## 7. 변경 전 구현과 다른 점

변경 전 앱은 `PERCENT / QUANTITY / PASS_FAIL` 및 시간 효과 중심이다. 이 절은 변경 전 구조를 기록한다. 데일리/Quest 유형·조건별 선택 복수 보상·스티커 구간은 이번 v2에 추가했고 기존 모듈은 별도 보존한다.

- `ParentRuleSettings.tsx`: 단일 폼, `rewardMinutes` 중심, 단계별 미완성 저장·보상 2개 입력 없음.
- 룰 저장·게시·활동 확인 RPC: TIME_DELTA/TIME_MINUTES 효과 중심.
- `activity_occurrences / activity_occurrence_events`: 부모 확인·수행일/입력일·revision·멱등성 재사용 가능.
- `manual_money_rewards`: 수동 기간 금액, 여러 활동 조건 보상과 그대로 동일시하면 기간 유일 제약 충돌 가능.
- `manual_bonus_coupons`: 별도 자유 특별보너스이지 조건 연계 자동 보상 자체는 아님.
- 일반 시간 원장·사용 가능 잔액 연결은 여전히 별도 후속이다.

추가할 책임은 단계별 편집 초안, 활동 유형, 강화물 카탈로그, 조건/구간별 선택 보상 1~2개, 스티커 사건·기간 달성 근거, 원천이 있는 보상 권리다. 적용된 migration을 덮어쓰지 않고 추가 migration으로 확장한다.

## 8. 구현 검증 기준

| 사례 | 기대 결과 |
| --- | --- |
| Quest에 현금 1개만 등록 | 두 번째 보상 없이 유효 |
| Quest에 시간 1개만 등록 | 현금 필수 아님 |
| Quest에 현금+시간 등록 | 조건 달성 시 둘 다, 선택 지급 아님 |
| 같은 조건에 3개 보상 | 현재 기획의 최대 2개 검증에서 거절 |
| 두 번째 보상 제거 | 숨겨진 필수값 오류 없음 |
| 데일리 미확인 | hold, 0개 확정 아님 |
| PASS·칭찬 | 원문에 따라 하루 1개·2개 |
| 주간 5개·누적 8개 | 기본 보상·등록한 추가 보상, 기본 재발행 없음 |
| 추가 구간 없이 등록 | 기본 보상만으로 유효 |
| 조건별 보상 1개 등록 | 두 개 강제 없음 |
| 임시저장 후 재진입 | 미완성 단계부터 이어쓰기 |
| 과거 확인·동일 재전송 | 실제 기간 보존·중복 권리 없음 |
| Quest 수치 중립·기존 게시본 | 기존 규칙/기록 유지 |
| 부모·자녀·보기 전용 보호자 | 기존 쓰기/조회 권한 경계 유지 |
