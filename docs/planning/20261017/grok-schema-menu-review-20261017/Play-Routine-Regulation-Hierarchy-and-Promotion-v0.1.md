# 규정의 위계는 고정된 종류가 아니라 승인된 관계로 관리한다

Task 아래에 새로운 규정이 생길 수 있고, 독립 운영 영역이 되면 School을 Task·Quest·Lifestyle과 같은 위계로 둘 수 있다. 다만 하위 항목이 많다는 이유만으로 격상하지는 않는다. 독립 목적과 평가 원칙, 변경 주기, 적용 범위를 따로 관리할 필요가 있을 때 격상을 제안한다. 아래는 2026-10-17 사용자 방향을 반영한 추가 설계안이며, 기존 DB·운영 사이트에는 적용하지 않았다.

## School 예시: 번호 확장과 관할 분리를 구별한다

학교가 단순한 Task 활동이면 T-007 같은 개별 규칙으로 충분하다. 학교 고유의 출결·교사 피드백·학습 약속·스티커 집계 등 별도 규율이 필요하면, School 규정을 신설하고 학교 규칙의 관할을 옮기는 것이 맞다.

```text
처음                         분리·격상 이후
기본법                       기본법
├─ Task                      ├─ Task
│  └─ 학교 관련 규칙          ├─ Quest
├─ Quest                     ├─ Lifestyle
└─ Lifestyle                 └─ School
                                 └─ 학교 관련 규칙
```

이미 학교 하위규정이 독립된 규정 ID를 가지고 있었다면 그 ID를 유지하고 새 버전·위계 관계를 승인한다. 아직 하위규정 없이 Task에 개별 학교 규칙만 있었다면 School 규정 ID를 신설하고, 이동 대상 규칙을 명시한다. Task 전체를 School로 이름 바꾸거나 폐지하는 것은 아니다.

위계 이동만으로 같은 의무가 다른 의무가 되지는 않는다. 같은 목적·조건의 규칙은 내부 `rule_id`와 안정된 집계 범위를 유지하고 새 관할 관계를 남긴다. 의무·목적 자체가 달라지면 별도 규칙과 승계 관계를 만든다. 이는 기존 수명주기 설계의 ‘관리 목적이 달라지면 새 번호’ 원칙과 구별되는 조직 개편이다. [1]

## 현재 스키마에서 바꿀 점

현재 `doc_kind` ENUM과 `rule_identities.kind` CHECK는 TASK/QUEST/LIFESTYLE에 고정돼 있다. `enforce_rule_governing_kind()`도 같은 종류만 연결한다. 따라서 **현재 설계가 School 격상을 이미 지원한다고 볼 수 없다.** School 코드만 추가하는 것으로 끝나지 않으며, 규정 종류·관할 검증·UI 필터를 함께 개편해야 한다. [2]

승인된 규정 영역은 종류 카탈로그로 관리하고, 규정 정체성·원문 버전·위계 관계를 분리하는 것이 맞다. ‘School이라는 영역’과 ‘현재 기본법 바로 아래에 있다’는 서로 다른 정보다. 위계는 정확한 규정 버전 사이의 `GOVERNS` 관계와 효력 구간으로 기록한다. 공통 규율 참조·호환·승계는 다른 관계 종류로 구별한다.

관계 변경 기록에는 이전 관할, 이후 관할, 대상 규칙, 승인자, 사유, 효력 시작일과 변경 묶음을 남긴다. 순환 관할은 거절한다. 동시에 둘 이상의 상위 관할을 허용할 경우에는 명시적 공동 관할과 충돌 처리 규칙이 필요하며, 단순히 링크를 두 개 넣고 자동 합산하지 않는다.

화면 번호를 소속이나 깊이의 유일 근거로 삼지 않는다. 기존 T-007은 과거 문서·사건에서 계속 설명 가능해야 한다. School 소속 표시나 새 별칭이 필요하면 번호 매핑 이력으로 추가하고 과거 번호를 덮어쓰지 않는다. 학교 집계도 T-007 문자열 대신 내부의 안정된 집계범위를 사용한다.

**격상은 분류 변경이지 정산 리셋이 아니다.** 기존 스티커, 열린 주간 기간, 보상권, 이행 기록은 그대로 유지한다. 같은 주를 Task와 School에서 각각 지급하지 않는다. 진행 중 기간의 관할을 바꾸려면 별도 전환 결정을 승인하고, 그렇지 않으면 기존 기간의 확정 관할을 유지한다. [1]

## AI는 격상 후보를 제안하고 부모가 승인한다

Manus는 다음을 근거로 후보를 제안할 수 있다. 해당 묶음이 독립 목적을 갖는지, 고유 평가·예외가 반복되는지, 여러 규정에 걸쳐 중복 정의되는지, 개정 영향이 다른 Task와 분리되는지를 본다. 규칙 개수나 이름의 유사성은 단독 격상 근거가 아니다.

제안서는 ‘School을 독립시키면 줄어드는 중복’, ‘옮길 규칙과 남길 규칙’, ‘상위 원칙과의 충돌’, ‘열린 기간·보상에 대한 영향’을 포함한다. Grok는 반례와 과잉 분리 여부를 2차 검토한다. 부모가 승인한 뒤 변경 묶음으로 반영하며, AI 결과만으로 관할·규칙·원장을 바꾸지 않는다. 이 절차는 제안된 작업 방식이지 자동 감시나 상시 실행이 설정됐다는 뜻은 아니다.

## 그래프를 사용한다고 그래프 DB로 즉시 바꾸지는 않는다

규정은 노드이고 위계·근거·승계·호환은 관계이므로 의미상 그래프다. 이 관계를 PostgreSQL 테이블로 저장하고 재귀 쿼리로 하위 규정과 영향 경로를 찾을 수 있다. PostgreSQL은 `WITH RECURSIVE`와 순환 탐지 기능을 지원한다. 순환 탐지 쿼리가 있다는 것과 입력 시 순환을 자동 거절하는 제약이 있다는 것은 다르므로, 게시 검증에도 연결해야 한다. [3]

관계가 여러 단계로 늘어나도 그것만으로 DB 교체 사유는 아니다. 복잡한 경로 분석이 주요 업무가 되고, 실제 데이터·조회 패턴에서 관계형 조회가 한계에 도달했는지 측정한 뒤 그래프 확장이나 별도 읽기용 그래프를 검토한다. 보상·횟수·불변 원장은 PostgreSQL 정본을 유지하는 것이 현재 구조에 맞다.

Apache AGE처럼 PostgreSQL에 그래프 기능을 추가하는 선택지도 있다. 다만 현재 Supabase 프로젝트에 설치 가능하다는 것은 확인하지 않았으므로, 즉시 사용 가능한 기능으로 제시하지 않는다. 별도 그래프를 쓰더라도 복제된 분석용 관계와 정본의 승인 버전이 어긋나지 않게 관리해야 한다. [4]
