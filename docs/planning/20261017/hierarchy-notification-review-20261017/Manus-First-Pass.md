# 규정 격상·격하와 보상 분리, 승인 알림·이력 — 1차 설계

사용자 요청은 기존 School 격상 재귀 SQL과 규정형 구조를 실제 Grok에 검토하고, Supabase 처리 범위·보상에 적용할지·부모 알림·기록 방법을 설계하는 것이다. 운영 구현·배포·새 알림 발송을 요청한 것은 아니다. 실제 자녀 개인정보 없이 설계만 검토한다.

## Supabase 처리 범위

2026-10-17 현재 프로젝트 메타데이터 읽기 결과: PostgreSQL 17.11. pg_available_extensions에서 pg_cron, pg_net, pgmq가 조회되지만 installed_version은 모두 NULL. age는 조회되지 않는다. 이 결과를 Supabase 전체 서비스의 설치 보장 또는 이미 동작하는 자동화로 확대하지 않는다.

규정 ID/버전/관계, 재귀 조회, 가족 권한, 승인 RPC, 변경·알림 저장, 보상·원장 트랜잭션은 PostgreSQL 정본으로 처리한다. Supabase Auth와 RLS, Edge Functions·Queues·Cron·Realtime을 필요한 단계에 추가할 수 있다. 모델 추론은 외부 Grok/xAI이고, 이메일·LINE·모바일 푸시는 별도 전달 경로다. 앱 화면은 React/Netlify에 남는다. ‘Supabase 플랫폼 중심으로 관리 가능’과 ‘모든 기능이 PostgreSQL 안에서 실행됨’을 구별한다.

Edge Functions는 함수 지속시간과 요청 idle 제한이 있으므로 긴 Grok 검토를 DB 승인 트랜잭션이나 부모의 브라우저 요청에 묶지 않는다. 짧은 SQL 트랜잭션으로 작업을 큐에 기록하고 작업자가 실행한다. 장시간 작업은 분할 또는 별도 앱 작업자가 필요할 수 있다. 큐의 visibility timeout 뒤 재전달을 가정하고 업무·알림의 멱등 키를 반드시 둔다. 실전 설정은 아직 하지 않는다.

## 위계 개편과 보상 변경의 분리

위계 관계 GOVERNS와 개정/승계/호환 관계는 다른 종류다. Task 아래 School 규정이 기본법 직속으로 이동해도 같은 목적의 규정·개별 규칙 ID와 안정된 집계범위는 유지한다. 기존 doc_kind ENUM, rule_identities.kind CHECK, 관할 종류 검증은 세 종류 고정이므로 리팩터링이 필요하다. 현재 설계가 이미 SCHOOL을 지원한다고 주장하지 않는다.

위계 관계만 바뀌었다면 보상 액수·스티커 종류·인정 횟수·기간 키·기발행 보상권·실제 이행·원장은 변경하지 않는다. 보상 종류/카탈로그가 늘었다는 이유로 같은 격상 개념을 자동 적용하지 않는다. 규정 위계와 자산 분류는 다른 관계다. 동일한 버전·이력·승인 패턴은 강화물 정의와 보상 정책의 변경에도 재사용할 수 있지만 내용과 적용 검증은 다르다.

상위 관할이 바뀌면 영향 분석은 필수다. Task에 있던 상한·배타 조건·학교 집계 정책이 새 School에도 정확히 연결되는지 확인한다. 기본 금액은 같아도 상한 상속이 빠지면 효과가 달라지므로 ‘영향 없음’을 추정하지 않는다. 영향 항목을 관할만 변경, 계산 변경, 사실/기간/권리 재검토로 분리한다. 계산 계약을 유지할 수 없다면 별도 보상 개정과 전환 승인 전에는 새 조합 게시를 막는다.

학교 동일 주간 0~4개 0원 / 5~7개 10,000원 / 8개 이상 최종 15,000원. 10,000원 유효 권리가 이미 있으면 신규 5,000원이며, 실제 이행액은 권리 발행 계산에서 다시 빼지 않는다. School로 격상/격하됐다는 이유로 같은 주를 새 scope로 열거나 누계를 리셋하지 않는다. 열린 기간은 당시 관할 묶음을 유지하고 새 기간 적용을 기본 제안으로 삼되 시행일은 부모가 승인한다.

## 후보 탐지와 부모 알림

현재 부모 한 명 운영에는 ‘규정’ 메뉴에서 ‘구조 점검’ 버튼으로 수동 검토하는 것이 가장 간단하다. 자료 변경 직후 가벼운 결정론적 분석으로 독립 목적/중복 정의/고유 평가/반복 예외를 후보로 묶을 수 있다. 의미 판단은 AI 제안이지 확정이 아니다. 격하는 독립 목적·운영 영역의 통합 여부를 검토하며 사용 빈도가 낮다는 이유만으로 제안하지 않는다. 격하는 폐지·삭제·보상 감소가 아니다.

Manus 역할의 1차 분석은 지금처럼 명시적 검토를 수행하거나, 나중에 별도 승인·배포된 분석 작업자가 수행한다. Supabase를 쓰면 Manus 에이전트가 자동 생기는 것으로 설명하지 않는다. Grok는 익명화된 근거와 영향 범위를 2차 검토한다. 상시 에이전트나 미래 예약을 이 설계만으로 생성하지 않는다.

앱 상단 ‘규정’에 검토대기 숫자, 운영표 위에는 낮은 우선순위의 요약 카드만 표시한다. 부모의 할 일 입력을 전체 화면으로 막지 않는다. 제안 카드에는 변경 전후 구조, 대상 규칙, 줄어드는 중복, 반례, 예상 효과와 시행 후보일을 표시한다. 보상 영향 검토 결과를 확인하지 않은 상태에는 ‘영향 없음’이 아니라 ‘미검토’로 표시한다. 부모는 ‘검토/보류/기각’을 선택한다. 실제 변경 승인에서는 정확한 변경 버전과 시행일을 다시 보여주고 승인받는다.

읽음은 승인과 다르다. 보류에는 사용자가 정한 재검토 시점/조건을 저장한다. 기각된 동일 대상·동일 입력 버전 제안은 반복 알림하지 않는다. 입력 버전이나 중요 근거가 바뀌면 이전 제안의 후속으로 기록하고 다시 검토할 수 있다. 예: family_id + 대상 규정 ID 묶음 + 입력 스냅샷 해시 + 제안 유형으로 중복 키를 구성한다.

외부 알림은 앱 알림의 보조 경로로, 원하는 경우 이메일/LINE을 별도 연결·동의 후 사용한다. 기본은 앱 재접속에도 남는 DB 알림이다. Realtime은 갱신 신호이며 전달 성공·읽음·승인의 정본이 아니다. 신호를 놓치면 알림 목록을 재조회한다. 외부 메일/메신저에는 자녀 이름·약물·행동 상세를 넣지 않고 인증된 앱의 제안 링크만 보낸다.

## 최소 기록 관계와 승인 동시성

새 엔티티 제안: governance_proposals(제안 정본), governance_proposal_items(대상별 전후 버전/관계), governance_reviews(AI/수동 검토 결과), governance_proposal_events(상태변경 이력), governance_change_sets(승인한 적용 묶음), notification_outbox(전달할 작업). 기존 앱 알림 테이블은 수신자 알림함으로 재사용 가능한지 별도 확인한다. 승인자·읽음 상태를 모델 응답이나 알림 전달 기록에 섞지 않는다.

제안 정본에는 family_id, proposal_id, 유형(PROMOTE/DEMOTE/REPARENT), 이유, 근거 버전·해시, 제안 대상, 이전/이후 관할, 영향 분류, 생성 주체·시각을 남긴다. 검토에는 모델 ID, 입력 해시, 완결 여부, 결과와 반론을 저장하고 토큰/비밀값은 남기지 않는다. 상태는 REVIEWING -> READY -> APPROVED/REJECTED/DEFERRED/SUPERSEDED, 승인한 변경 묶음에는 SCHEDULED/APPLIED/FAILED를 별도로 둔다. 읽음은 수신자 알림의 상태다.

승인 RPC는 인증된 활성 부모의 가족 권한을 확인하고 제안/영향 대상에 잠금을 잡는다. 부모가 본 expected_revision/기준 버전과 현재 상태를 비교한다. 변경됐으면 재검토하고 자동 승인하지 않는다. 같은 request_id로 재전송하면 같은 승인/변경 묶음을 반환한다. 규정 관계의 순환·동일 시점 복수 관할·기간 경계·호환·보상 의미 보존을 확인한다. 여러 관련 변경은 하나의 트랜잭션으로 묶고, 외부 Grok나 이메일 호출은 그 트랜잭션 밖에서 수행한다.

변경 묶음은 미래 효력을 가진 새 관계·버전·이력을 추가한다. 게시된 옛 관계와 원문을 덮어쓰지 않는다. 미래 관계의 효력에는 승인 시간과 실제 적용기간을 구분한다. 이미 열린 기간·기존 사건은 당시 묶음을 고정 참조한다. 적용 이후 구조 화면은 효력 날짜에 맞춰 새 관계를 읽고, 과거 화면은 옛 관계를 읽는다.

알림을 DB에 저장하고 outbox에 작업을 넣는 것은 같은 짧은 트랜잭션에서 처리한다. 전송 시도는 별도 append-only 이벤트로 provider_message_id, 상태/오류코드, 시각을 기록한다. 외부 제공자가 멱등을 지원하지 않으면 중복 전송 가능성은 남으므로, 정확히 한 번 전달을 보장한다고 주장하지 않는다. 실패 재시도·장기 실패 목록과 운영자 확인 경로가 필요하다. 앱 알림 자체는 중복 키로 한 건만 생성한다.

## 남는 구현 조건

개념 설계/격리 샘플/현재 운영 구현을 구분한다. 실제 프로젝트에는 스케줄·큐를 켜지 않았다. 가족별 FK·RLS·RPC/함수 최소 권한과 test_mode 제거, 계층 구조와 정정 동시성의 실다중연결 시험이 필요하다. 증거/검토 원문은 민감도에 따라 접근을 제한하고 유지기간·삭제 정책을 정한다. 익명화된 구조 검토만 외부 모델에 보내는 것이 기본이다.

공식 참고: Supabase Cron https://supabase.com/docs/guides/cron ; Queues https://supabase.com/docs/guides/queues ; Edge Functions 제한 https://supabase.com/docs/guides/functions/limits ; Realtime 권한 https://supabase.com/docs/guides/realtime/authorization ; Database Webhooks https://supabase.com/docs/guides/database/webhooks .

## 기존 운영 코드에서 별도로 확인한 알림·감사 경계

읽기 전용 소스 점검 결과, 기존 public.notifications는 0002_auth_workflows.sql에 존재하고 id/family_id/recipient_principal_id/notification_type/title/body/metadata/read_at/created_at 필드를 가진다. 기존 enum은 자녀 연결·해제·초대 거절·만료용이므로 신규 제안/적용/실패 유형은 추가 계약이 필요하다. 부모별 알림 행과 read_at만 수정 가능한 최소 권한 패턴은 재사용할 수 있다. 그러나 현재 client/src에 이 notifications를 읽는 알림함 UI/API는 확인되지 않아, 신규 상단 알림을 이미 구현된 것으로 설명하면 안 된다.

routine_request_events와 routine_entitlement_events는 특정 routine 요청·보상권용 불변 기록이다. 새 규정 제안의 상태 정본을 이 테이블에 무리하게 넣지 않는다. 제안/검토/전환 이력은 별도 정본을 만들고 기존 이력과 연결할 수 있다. 현 GUARDIAN은 상태창 전용 RPC와 제한 투영을 사용하므로 승인 제안 원문·판단 권한을 확장하지 않는다. 새 승인/기각/보류 RPC는 활성 OWNER_PARENT/PARENT의 family 소속을 다시 확인해야 한다. 알림 조회도 제안 알림에 대해서는 수신자 조건 외에 현재 가족의 부모 권한이 여전히 유효한지 확인해야 한다.

이 근거는 소스 확인이며 오늘 실제 알림을 보내거나 신규 테이블을 설치했다는 뜻이 아니다.
