# 규정 격상·격하, 보상 영향과 부모 알림·기록 설계 v0.2

**Supabase를 규정·승인·알림·보상 기록의 중심으로 유지하면 된다. 규정의 격상·격하를 보상이나 스티커에 자동 전파하지 않고, 계산 의미가 유지되는지 검증한 뒤 관할 관계만 바꾸는 구조가 맞다.** 부모에게는 작은 제안 카드로 알리고, 실제 변경은 검토한 버전과 시행일을 명시해 승인받는다.

작성일: 2026-10-17. Manus 1차 설계와 재귀 SQL에 대한 실제 Grok-4.7 검토를 반영한 후속안이다. Grok 응답은 완결됐지만 이 v0.2를 다시 검증한 것은 아니다. 현재 운영 DB·공개 UI에는 이 기능을 설치하지 않았으며, 미래 자동화나 외부 알림도 설정하지 않았다. [7]

## 1. Supabase에서 가능한 처리와 외부에 남는 처리

규정 ID·원문 버전·위계 관계, 날짜별 재귀 조회, 가족 권한, 부모 승인 RPC, 제안 상태와 변경 이력, 보상·원장 트랜잭션은 PostgreSQL을 정본으로 삼을 수 있다. Supabase 데이터베이스 함수를 앱에서 RPC로 호출하는 방식에 맞는다. 단, SECURITY DEFINER 함수는 RLS를 우회할 수 있으므로 함수 본문에서 가족·역할을 확인하고 실행 권한을 좁혀야 한다. [6]

**현재 프로젝트를 읽기 전용으로 확인한 결과 PostgreSQL 17.11이었다.** `pg_cron`, `pg_net`, `pgmq`는 사용 가능 확장 목록에 있었지만 설치 버전은 모두 NULL이었다. `age`는 그 목록에서 조회되지 않았다. 따라서 현재 예약 검토·작업 큐·웹훅이 이미 작동하거나 AGE를 바로 설치할 수 있다고 설명하면 안 된다.

필요해지면 Supabase Cron으로 구조 점검 작업을 예약하고, Queues에 검토·전달 작업을 보관하며, Edge Functions에서 외부 모델 API를 호출할 수 있다. Cron은 작업 실행 이력을 저장하고, Queues는 작업을 내구성 있게 보관한다. 다만 큐 메시지 재전달과 처리 재시도를 가정해 업무별 중복 방지를 별도로 둬야 한다. [1] [2]

**Grok 추론 자체와 이메일·LINE·휴대폰 푸시의 실제 전달, React/Netlify 화면까지 모두 PostgreSQL 내부에서 처리되는 것은 아니다.** Supabase는 저장·권한·실행 연결의 중심이고, 모델과 외부 전달 경로는 별도 연동이다. 현재 이미지 서버도 Sharp를 사용하므로 앱 전체를 Edge Functions로 그대로 옮기는 것과 이번 규정 처리 가능 여부는 다르다. 공식 제한에는 Sharp 같은 일부 Node 라이브러리의 제약이 명시돼 있다. [3] [5]

긴 Grok 검토를 부모의 승인 요청이나 DB 트랜잭션 안에서 기다리게 하지 않는다. 공식 Edge Functions 제한은 요청 idle 150초, worker 지속시간은 플랜에 따라 150초 또는 400초다. 작업을 먼저 저장하고 별도 실행하며, 긴 검토는 분할하거나 기존 앱의 작업자에서 처리할 수 있어야 한다. 이번 실제 검토도 요청부터 완결까지 약 3분이 걸렸으므로 짧은 승인 RPC에 묶으면 안 된다. [3] [7]

## 2. 보상에도 ‘격상’을 적용해야 하는가

**규정 위계와 보상 분류는 서로 다른 관계다.** Task 아래 School을 기본법 직속으로 옮기는 일과, 시간 쿠폰·현금·쿠페이머니·소원을 분류하는 일은 같은 트리를 공유하지 않는다. 규정의 위계 변경으로 자산을 재분류하거나 단위·잔액을 환산하지 않는다.

다만 ‘영구 ID + 정의 버전 + 변경 이유 + 승인 + 과거 참조 보존’이라는 공통 관리 방식은 강화물 정의와 보상 정책에도 재사용할 수 있다. 보상 종류가 늘면 기존 카탈로그를 확장한다. 조건당 보상 개수나 지급 방식 자체를 바꾸면 별도의 정책 개정이다. 규정 격상 승인이 보상 변경 승인까지 대신하지 않는다.

School이 독립해도 기존 `rule_id`, 안정된 학교 집계범위, 학교 스티커의 원천, 열린 주간 기간, 기발행 보상권과 실제 이행 기록을 유지한다. **격상·격하는 보상 초기화도, 증액·감액도 아니다.** 격하는 독립 영역을 다른 영역 밑으로 통합하는 조직 변경이며 폐지·삭제와도 다르다.

학교 최고 구간의 최종총액은 그대로다. 0~4개는 0원, 5~7개는 10,000원, 8개 이상은 총 15,000원이다. 같은 기간에 유효한 10,000원 권리가 있으면 신규 발행은 5,000원이다. 실제 이행액을 발행식에서 다시 빼지 않는다.

Grok가 짚은 반례는 중요하다. 격상하면서 새 집계범위나 새 기간을 만들면 기존 10,000원이 없는 것처럼 계산해 15,000원을 다시 발행할 수 있다. 금액이 같아도 Task에 있던 상한·배타 조건이 School에서 빠지면 실질 보상이 달라진다. 따라서 ‘보상 영향 없음’은 AI의 문장 판단이 아니라 정확한 기준 버전·계산 계약을 대조한 결과여야 한다. [7]

## 3. ‘관할만 변경’인지 확인하는 게시 조건

격상·격하 제안에는 변경 전후의 규정 버전과 대상 규칙을 고정한다. 그 묶음에서 측정 방식, 인정 횟수, 기간 경계, 배타 조건, 상한, 강화물 버전과 효과 수량, 집계범위가 유지되는지 확인한다. 규정 종류를 바꾸었다는 이유로 PASS가 점수제로 바뀌는 식의 처리기 전환도 허용하지 않는다. 실행 계약은 이름이나 위계 깊이가 아니라 승인된 측정·효과 정의를 참조해야 한다.

검토 결과는 ‘관할만 변경’, ‘계산 계약 변경 필요’, ‘기간·권리 재검토 필요’, ‘미검토’로 구분한다. 미검토를 영향 없음으로 표시하지 않는다. 상위 상한 연결이 끊기거나 현재 처리기가 School을 지원하지 않으면 게시를 막는다. 현재 설계의 `doc_kind`, `rule_identities.kind`와 관할 종류 검사도 세 종류에 고정돼 있어 함께 개편해야 한다. [7] [8]

기존 사건과 열린 기간은 당시 관할 묶음을 유지한다. 새 관계는 승인한 시행일과 적용 범위를 따른다. 다음 온전한 기간부터 적용하는 것을 기본 제안으로 삼을 수 있지만, 주간 경계와 시행일은 사용자 확정값이 아니다. 진행 중 기간에 적용하려면 별도 전환 조항을 승인해야 한다.

## 4. 난영님에게 알리는 방식

현재 한 부모 운영에는 **규정 메뉴의 ‘구조 점검’ 버튼과 앱 안의 검토대기 알림**부터 두는 것이 적절하다. 상시 AI를 돌리거나 구조 제안을 매일 할 일로 만들 필요는 없다. 월별 계획 준비나 중요한 규정 개정 중에 명시적으로 점검하면 된다.

향후 자동 후보 탐지를 붙인다면 규정 저장·개정 사건을 계기로 가벼운 구조 분석을 실행한다. 독립 목적·고유 평가·중복 정의·반복 예외가 있는지를 근거로 삼고, 항목 수나 사용 빈도만으로 격상·격하를 결정하지 않는다. 의미 판단은 Manus 역할의 1차 분석과 Grok 반례 검토를 거친 제안이다. Supabase에 규칙을 넣었다고 Manus 에이전트가 자동 생성되는 것은 아니므로 작업자와 호출 경로를 별도 구현해야 한다.

상단 ‘규정’에 검토대기 숫자를 보여주고, 운영표에는 다음과 같은 작은 카드를 둔다. 전체 화면으로 부모의 체크를 막지 않는다. 아래는 표시 예시이지 실제 알림 발송 결과가 아니다.

> **School 독립 규정 제안**
>
> 현재: 기본법 → Task → School
>
> 제안: 기본법 → School
>
> 이유: 학교 고유 평가와 개정 범위를 독립 관리할 수 있음.
>
> 보상 영향: 상한·집계 계약 검토 필요. 이번 주 스티커·권리 초기화 금지.
>
> **자세히 검토 / 나중에 / 기각**

‘자세히 검토’ 화면에서는 전후 관계, 이동할 규칙과 남길 규칙, 근거와 Grok 반론, 보상 영향 결과, 시행일을 보여준다. 이 화면에서 정확한 변경 묶음을 승인한다. 별도 체크 단계를 반복해서 만들지 않고 한 번의 명확한 승인으로 처리한다.

**알림을 읽었다는 것은 승인했다는 뜻이 아니다.** ‘나중에’는 부모가 선택한 재검토 시점이나 조건을 기록한다. 기각한 동일 대상·동일 입력 버전의 제안은 반복 알리지 않는다. 중요한 근거나 버전이 달라졌을 때만 이전 제안의 후속으로 기록하고 다시 검토한다.

앱 알림은 DB에 남겨서 로그아웃·새로고침·다른 기기 접속 후에도 확인할 수 있게 한다. Realtime은 화면 갱신 신호로만 사용하고, 접속이 끊겼거나 신호를 놓치면 목록을 다시 조회한다. Realtime Broadcast 자체는 영구 알림 저장소가 아니며 권한 설정도 필요하다. 외부 이메일·LINE은 사용자가 채널을 정한 뒤 보조 경로로 연결한다. 그 메시지에는 아이 행동·복약 상세 대신 인증된 앱의 제안 링크만 넣는다. [4] [5]

## 5. 무엇을 어떻게 기록할 것인가

처음부터 별도 관리 페이지를 여러 개 만들지 않고, 다음 세 가지 정본과 기존 알림함을 연결한다. 여러 대상의 구조 변경을 다루게 되면 대상 항목의 자식 표를 추가하되 부모 입력 단계는 늘리지 않는다.

`governance_proposals`는 제안 정본이다. 가족, 대상 규정 ID, 격상·격하·관할 이동 유형, 전후 버전·관계, 근거 스냅샷 해시, 보상 영향 검토 결과, 생성 주체·시각과 현재 상태를 보관한다. 같은 대상·같은 근거 버전·같은 제안 유형의 중복 생성을 막는다.

`governance_proposal_events`는 지우지 않는 이력이다. 생성, AI 검토 완료·실패, 부모 보류·기각·승인, 철회·기준 변경 사건마다 행을 추가한다. 사건 ID, 제안 ID, 실제 행위자, 이전/이후 상태, 사유, 서버 기록 시각과 요청키를 남긴다. Grok 모델 ID·입력 해시·완결 여부·반론과 원문 참조도 검토 사건에 연결한다. 큰 원문은 접근 제한된 저장소 참조로 분리할 수 있다. 토큰과 비밀값은 저장하지 않는다.

`governance_change_sets`는 승인한 적용 묶음이다. 승인자·승인 시각, 시행일·적용 범위, 기준 버전·제안 revision, 새 규정/관계 버전과 처리 결과를 고정한다. ‘승인됨’과 ‘실제로 적용됨’을 분리하고, 예약·적용·실패 상태와 적용 이력을 남긴다. 즉시 적용이면 승인 RPC가 검증과 게시를 하나의 트랜잭션으로 처리하고, 미래 적용이면 승인한 관계·버전을 준비한 뒤 효력/적용 절차를 구현해야 한다. 자동 적용 경로가 준비되지 않은 상태를 ‘적용 완료’로 표시하지 않는다.

기존 앱에는 `public.notifications`가 있다. 수신자별 행과 `read_at` 수정 패턴을 재사용할 수 있다. 다만 현재 유형은 자녀 연결·해제·초대 관련이고, 그 표를 읽는 알림함 UI는 현재 소스에서 확인되지 않았다. 새 제안/적용/실패 유형과 부모 알림 UI를 추가해야 한다. `routine_request_events`와 `routine_entitlement_events`는 특정 활동·보상권 이력이지 새 제안 상태 정본이 아니므로 억지로 합치지 않는다.

알림 기록에는 `proposal_id`와 수신자, 읽은 시각을 연결한다. 승인 상태는 제안/적용 묶음에 남긴다. 외부 전송을 붙일 때만 `notification_outbox`와 전달 시도 이력을 추가한다. 전송 시각, 경로, 제공자 메시지 ID, 실패코드와 재시도를 보관한다. 큐 처리 완료·메일 수락·부모 읽음·부모 승인·규정 적용은 서로 다른 사건이다.

## 6. 저장·승인·알림이 꼬이지 않게 하는 처리

제안과 앱 알림을 생성하는 것은 같은 짧은 트랜잭션으로 묶는다. 외부 검토나 메일 호출은 밖에서 수행한다. 모델 호출이 실패하면 ‘검토 실패/재시도 가능’으로 남기고 기존 운영을 유지한다. 완결되지 않은 모델 응답으로 승인 가능한 제안을 만들지 않는다.

승인 RPC는 활성 OWNER_PARENT/PARENT와 가족 소속을 서버에서 확인한다. 자녀와 상태창 전용 보호자에게 제안 승인·기각·상태 변경 권한을 주지 않는다. 제안 알림 조회에도 수신자 조건뿐 아니라 현재 유효한 부모 권한을 적용한다.

부모가 본 제안 revision·입력 해시와 실제 최신 버전을 잠금 후 비교한다. 다르면 ‘검토 이후 규정이 바뀌었습니다’로 승인하지 않고 재검토한다. 동일 요청키의 재전송에는 기존 승인 결과를 돌려준다. 같은 가족의 경쟁하는 구조 변경은 공통 잠금이나 동등한 직렬화로 순환·복수 관할 검사를 원자적으로 처리해야 한다. 단순히 사전 SELECT에서 순환이 없었다는 것으로 동시 변경까지 안전하다고 볼 수 없다.

기존 게시 원문과 관계는 덮어쓰지 않는다. 관계 종료 사건과 새로운 관계/버전으로 시점별 위계를 구성한다. 현재 관계 표의 ‘양끝 버전+관계’ UNIQUE는 같은 연결을 다시 시행하는 일반 이력까지 표현하기에 부족하므로, 관계 정체성과 효력 버전/사건의 구조를 보완해야 한다. 재귀 SQL의 `CYCLE` 표시는 입력 차단을 대신하지 않는다. [7] [8]

외부 전송은 중복이나 재시도가 생길 수 있다. 앱 알림 한 건은 DB 중복키로 보장하고, 외부 경로는 제공자의 멱등 지원을 활용하되 정확히 한 번 전달을 약속하지 않는다. 장기 실패는 별도 실패 목록에 남겨 부모 알림 정본을 잃지 않는다. [2]

## 7. 먼저 만들 것과 나중에 붙일 것

먼저 만들 것은 규정 메뉴의 수동 점검, 세 정본, 기존 알림함과 상단 작은 카드, 부모 권한·기준 버전 검사, 관할만 변경할 때의 보상 의미 보존 검증이다. 다음으로 필요한 때에만 검토 큐·예약 적용·외부 알림을 붙인다. 그래프 DB 교체나 상시 Manus 호출은 선행 조건이 아니다.

운영 연결 전에는 두 브라우저 동시 승인, 기각 후 동일 제안 재전송, 검토 중 규정 개정, 미래 적용일 경계, 이미 열린 학교 주간, 보상 10,000원→15,000원 구간, 알림 신호 유실 후 재조회와 외부 전송 실패를 실제로 시험해야 한다. 오늘 수행한 것은 Grok 검토와 프로젝트 메타데이터 조회이며 이런 운영 동시성 시험을 완료했다는 뜻은 아니다.

Grok 원문의 ‘운영 regulation_version_relationships’ 표현은 이번에 검토한 **새 설계의 표**에 대한 지적이지, 현 운영 Supabase에 그 신규 표가 배포됐다는 확인이 아니다. 이미 구현된 부모·자녀 연결과 신규 법령 설계를 혼동하지 않는다. [7]

알림 채널·상시 검토 주기·보존 기간은 아직 선택하지 않았다. 민감한 원문은 필요한 접근과 보존 범위를 정하고, 삭제가 필요한 개인정보와 보존할 승인 증거를 구분해야 한다. 감사 이력을 불변으로 둔다고 개인정보를 무기한 보관하자는 뜻은 아니다.
