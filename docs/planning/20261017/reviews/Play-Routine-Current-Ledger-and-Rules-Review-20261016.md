# Play Routine — 현재 원장·규칙과 운영방식 대조표

**결론부터 말하면, 현재 앱은 ‘룰 등록·자녀 배정·부모 확인·보상 권리’까지 구현되어 있습니다. 기존 운영에 필요했던 ‘횟수 제한·생활습관의 하루 다회 기록·독립 패널티·통합 원장’은 충분히 구현되지 않았습니다. 화면을 더 다듬기보다 이 운영 관계를 먼저 보완하는 것이 맞습니다.**

기존 입력을 지우고 다시 만들 필요는 없습니다. 가족 연결, 활동, 강화물, 게시 룰과 확인 사건 구조는 재사용할 수 있습니다. 이번 작업은 **조회와 정리만** 했습니다. DB 변경, 룰 수정, 새 배정, 게시, 보상 지급, 코드 배포는 하지 않았습니다.

기준은 2026-10-16 오전의 실제 Supabase 읽기 전용 조회, 현재 소스와 사용자 제공 시트입니다. 링크의 `gid=1385231187`은 `01_node_types`입니다. 운영 조건은 같은 문서의 `03_nodes`, `04_edges`, `05_rule_conditions`, 원장은 `11_coupon_ledger`와 `12_daily_balance_snapshots`까지 함께 읽었습니다. 이전 시트의 값은 비교 자료이며 새 앱에 이관하거나 그대로 재활성화하라는 뜻은 아닙니다. [1]

## 1. 현재 ‘원장’은 어디까지 있는가

**보상 권리를 기록한 것과 사용 가능한 잔액 원장을 만든 것은 다릅니다. 현재 운영 Supabase에는 통합 시간·돈 원장이 없습니다.** 실제 업무용 `public` 테이블 38개와 `private` 업무 테이블 목록을 확인했고, 적용 migration은 19개였습니다. 아래의 미구현은 단순 화면 숨김이 아닙니다.

| 층 | 현재 실제 구조 | 현재 하는 일 | 빠진 일 / 주의 |
|---|---|---|---|
| 부모·자녀·가족 | `principals`, `families`, `family_memberships`, `child_profiles` | 실제 부모·자녀를 별도 계정으로 연결 | 현재 부모 1명·자녀 1명 ACTIVE 연결 확인 |
| 승인된 활동 종류 | `ref_concepts`, `ref_concept_types` | 활동의 안정적인 식별자와 종류 보관 | 스티커 종류 정본과 동일한 테이블은 아님 |
| 강화물 카탈로그 | `routine_reinforcers` | 돈·분·포인트·소원 이름과 단위 등록, 여러 활동에서 재사용 | 패널티 종류 카탈로그는 없음 |
| 규칙 작성 | `routine_drafts` | 단계별 임시저장·이어쓰기 | 임시저장만으로 활동이나 보상을 발생시키지 않음 |
| 게시 규칙 | `routine_rules`, `routine_conditions`, `routine_reward_items` | 데일리/Quest, 구간, 조건별 보상 1~2개 동결 | 하루/주간 최대 인정 횟수와 자산별 상한 정책 없음 |
| 자녀 배정 | `routine_assignments` | 요일 반복·한 번 수행·시작일/종료일 | 같은 활동의 하루 N회 슬롯 없음 |
| 오늘/과거 수행 | `routine_occurrences` | 수행일별 자녀 보고·부모 확인·점수·PASS·스티커 | 같은 배정은 하루 한 행. 여러 회 수행을 분리할 수 없음 |
| 액션 이력 | `routine_occurrence_events`, `routine_request_events` | 확인·정정·중복 요청의 감사 근거 | 액션 이력이 있다고 잔액 원장이 완성된 것은 아님 |
| 조건 달성 보상 권리 | `routine_entitlements`, `routine_entitlement_events` | 조건 달성 시 어떤 보상을 받을 권리가 생겼는지 기록 | 시간 사용 가능 잔액의 입출금이 아님. 이행 확인도 실제 자동 송금이 아님 |
| 자유 특별보너스 | `manual_bonus_coupons` | 부모가 별도 보너스 쿠폰 발행·이행 기록 | 활동의 정규 구간 보상과 출처가 다름 |
| 수동 기간 돈 보상 | `manual_money_rewards`, `manual_reward_events` | 일·주·월·이벤트 금액과 지급 확인 | 자동 결제나 통합 돈 원장이 아님 |
| 구버전 규칙·확인 | `policy_*`, `activity_assignments`, `activity_occurrences` | 이전 시간 중심 룰과 기록 보존 | 신버전과 병존. 현재 시간 티켓의 예정분은 구버전 계산 경로 |
| 패널티 | Quest의 `penaltyLimit`, `penaltyMinutes`; 구버전 음수 예정분 | 낮은 점수의 차감 **후보** 표시 | 독립 패널티 등록·승인 거래·실제 원장 차감 없음 |
| 사용 가능 원장 | **미구현** | — | 확정 보상·차감·사용·취소·상쇄를 합산하는 시간/돈/포인트 원장 필요 |
| 자정 정산 | **미구현** | — | 확정 사건을 언제 어떤 거래로 옮길지 결정하는 정산 실행 필요 |
| 잔차와 잔차 결정 | **미구현** | — | 분류 불명·판정 불명 사건을 보관하고 승인된 종류로 연결하는 큐 필요 |
| 일별 잔액 스냅샷 | **미구현** | — | 그날 확정 잔액·hold·차감 대기를 보관하는 관측 기록 필요 |

게시 규칙의 내용과 강화물 이름·값을 동결한 ‘스냅샷’은 있습니다. 그러나 이것은 **일별 잔액 스냅샷이 아닙니다.** 저장소에 별도 MySQL/Drizzle 원장 시제품과 설계 파일이 있어도 현재 부모·자녀 Supabase 운영 경로에 연결된 원장으로 간주할 수 없습니다. [2] [3]

## 2. 지금 입력한 룰 — 실제 저장값

신버전 **게시 룰 5개, 조건 6개, 연결 보상 7개, 강화물 4개**가 저장되어 있습니다. 강화물은 미디어 쿠폰(분), 소원(내용), 용돈(원), 쿠페이머니(포인트)입니다. 잘못 등록했던 ‘밀크티 학습지’ 강화물은 없고, **활동으로 등록한 ‘밀크티 학습지’는 남아 있습니다.**

| 실제 게시 룰 | 측정·아이콘 | 실제 달성 조건 | 연결 보상 | 효력 시작 | 현재 신버전 자녀 배정 |
|---|---|---|---|---|---|
| 학교생활 | 데일리·도장 `STAMP` | 주간 5개 / 누적 8개 | 5개: 쿠페이머니 10,000포인트. 8개: 추가 5,000포인트, 합계 15,000포인트 | 10/16 | 없음 |
| 밀크티 학습지 | 데일리·웃음 `SMILE` | 하루 1개 이상 | 미디어 쿠폰 40분 | 10/16 | 없음 |
| 기초연산 2000 | Quest·수량 `QUANTITY` | 80 이상. 60 미만은 패널티 후보 80분 | 미디어 쿠폰 120분 | 10/17 | **11/1 한 번 수행**으로 배정 |
| 기탄수학 G5 하루 3장, 나눗셈 | 데일리·별 `STAR` | 하루 1개 이상 | 미디어 쿠폰 40분 | 10/17 | 없음 |
| 기탄수학 G5 나눗셈 20문제 3분 시험 | Quest·백분율 `PERCENT` | 80% 이상. 60% 미만은 패널티 후보 120분 | 쿠페이머니 30,000포인트 **및** 미디어 쿠폰 120분 | 10/17 | 없음 |

**‘등록됐는데 오늘 자녀에게 안 보임’과 ‘저장 실패’는 다릅니다.** 현재 신버전 배정은 1건이고 그것도 11/1 일정입니다. 나머지 4개는 게시됐지만 배정되지 않았습니다. 이번 읽기 조회 시점에 신버전 수행·부모 확인 사건·보상 권리는 모두 0건이었습니다. 실제 운영 성공을 이미 누적한 상태로 볼 수는 없습니다.

별도로 **구버전 ‘밀크티’ 1건은 10/16부터 월~금 배정**되어 있습니다. 부모 확인 측정은 `PERCENT`, 80 이상이면 예정 40분이고 낮은 구간은 보상 없음·차감 0분입니다. 신버전 ‘밀크티 학습지’와 같은 학습을 뜻한다면, 두 등록기를 계속 동시에 쓰는 대신 기존 배정 종료와 새 배정 시작을 연결해야 합니다. 이름·활동 ID가 다른 경우 기존 중복 방지 장치만으로 의미상 같은 학습을 찾아내지는 못합니다. **현재 신버전 밀크티는 미배정이므로 두 배정이 이미 겹쳤다고 판정한 것은 아닙니다.** [2] [4]

### 입력 설명과 실제 판정이 다른 부분

여기는 자동으로 수정하지 않았습니다. 사용자가 적은 설명과 구조화된 조건이 다르므로 무엇을 정본으로 할지 확인해야 합니다.

| 룰 | 입력 설명 | DB가 실제 사용하는 값 | 현재 위험 |
|---|---|---|---|
| 기초연산 2000 | ‘20문제 시험, 80점 이상, 60점 이하 -1시간’ | 수량 방식 80 이상 / **60 미만**, 후보 **80분** | 점수와 수량이 다름. ‘이하’와 ‘미만’이 다르고 1시간과 80분도 다름 |
| 기탄수학 G5 나눗셈 20문제 3분 시험 | ‘3분 내 15문제 이상’ | 백분율 **80% 이상** | 20문제 중 15개는 75%. 80%는 16개에 해당. 3분 제한은 설명에만 있고 현재 단일 수치 판정은 시간과 정답 수를 함께 검사하지 않음 |
| 학교생활 | ‘쿠페이 머니 1만원 / 1.5만원’ | 자산 단위 **POINT·포인트** | 원화 지급과 서비스 포인트가 동일하다고 앱이 자동 환산하지 않음 |

현재 Quest는 `QUANTITY`를 선택해도 저장 점수 범위가 0~100입니다. 문제 수·반복 횟수가 100을 넘거나 시간과 정답률을 함께 측정하는 일반 엔진은 아닙니다. [2]

## 3. 스티커는 종류별로 구별되어 저장되는가

**활동별 기록은 구별됩니다. 그러나 ‘스티커 종류 DB’가 따로 있는 구조는 아닙니다.**

| 구분 | 현재 저장/계산 방식 | 의미 |
|---|---|---|
| 활동 구별 | 수행건이 `rule_id`, `assignment_id`, 자녀와 수행일을 참조 | 학교생활과 기탄 기록을 한 행으로 합치지 않음 |
| 스티커 그림 | 게시 룰의 `payload.stickerIcon`에 `STAR / SMILE / STAMP` 저장 | 별·웃음·도장 표시를 복원할 수 있음 |
| 하루 개수 | 부모 PASS=1, PASS+칭찬=2, 문제 있음=0 | 하루 최대 2라는 고정 구현. 부모가 활동별 허용 횟수를 등록하는 설정이 아님 |
| 부모 미확인 | 스티커 `null` | 0개 확정이 아닌 hold |
| 기간 합계 | **자녀 + 룰 버전 + 기간**의 스티커 합계 | 같은 별 아이콘을 쓰는 여러 활동이 자동 합쳐지지 않음 |
| 별도 스티커 종류 | `sticker_type_id` 카탈로그 없음 | ‘공부 스티커’, ‘생활습관 스티커’, ‘패널티 표식’의 독립 정본·합산 대상 관계 없음 |
| 아이콘 파일 | 화면의 아이콘 컴포넌트로 표시 | 스티커 이미지 파일/에셋 ID를 개별 저장하는 구조 아님 |
| 새 룰 버전 | 새 `rule_id` | 같은 활동의 주중 버전 변경을 하나의 주간 합계로 자동 이어 붙이지 않음 |

따라서 ‘패널티도 종류만 다르고 같은 등록·기록 방식을 쓰자’는 요구를 지금의 아이콘 enum만으로 충족할 수 없습니다. **그림은 표시이고, 종류 ID와 판정·효과 방향은 별도 관계**여야 합니다. 같은 도장을 골라도 보상과 패널티가 뒤섞여 계산되면 안 됩니다. [2] [5]

## 4. 기존 시트에 있던 횟수 제한 — 현재 앱에서 빠진 부분

아래는 시트 `05_rule_conditions`의 실제 `evaluation_scope`와 `evaluation_limit` 값입니다. ‘이 횟수 제한이 과거 Apps Script에서 언제나 정확히 강제됐음’까지 단정한 표는 아닙니다. 현재 Apps Script 원본은 이번 작업에서 확인하지 않았습니다.

| 기존 항목·조건 ID | 단위 효과 | 제한 기간 | 최대 인정 횟수 | 표의 값으로 계산한 기간 최대 효과 | 현재 지원 차이 |
|---|---:|---|---:|---:|---|
| 매일 공부 `COND_R01` | +60분 | 하루 | 1 | +60분 | 데일리 하루 한 건은 가능하지만 횟수 상한 정책 필드는 없음 |
| 숙제·유인물 챙기기 `COND_R02` | +40분 | 하루 | 1 | +40분 | 같은 차이 |
| 독서 토론 `COND_R03` | +60분 | 주 | 1 | +60분 | 스티커 구간은 가능. ‘1회 수행당 60분, 주 1회까지만’ 모델은 없음 |
| 방정리 `COND_R07` | +60분 | 주 | 2 | +120분 | ‘주 2회 각각 보상하고 세 번째는 기록만’ 설정 없음 |
| 남자화장실 청소 `COND_R08` | +5,000원 | 주 | 1 | +5,000원 | 수동 돈 기록/권리는 가능. 활동별 주간 지급 횟수 가드 없음 |
| 고양이 화장실 `COND_R09` | +20분 | 하루 | 2 | +40분 | **같은 활동 하루 두 번 수행·각각 확인·두 회까지만 보상 불가** |
| 9시 반 이전 취침 `COND_R11` | +30분 | 하루 | 1 | +30분 | 하루 PASS는 가능. 실제 시간 준수의 구조화된 검사 별도 필요 |

`COND_R09`는 특히 중요합니다. **조건표에는 하루 2회지만 `03_nodes` 메모에는 하루 1회**라고 적혀 있습니다. 둘 중 무엇이 최종 운영 규칙인지 원문 자체에 충돌이 있습니다. 이를 화면에서 임의로 정하지 않고 명시적 횟수 필드로 고정해야 합니다. [1]

### ‘하루 몇 회’와 ‘하루 얼마’는 다른 제한이다

| 구분 | 필요한 뜻 | 현재 상태 |
|---|---|---|
| 수행 기록 횟수 | 하루 실제 몇 번 했는가 | 배정당 하루 한 수행건만 가능 |
| 보상 인정 횟수 | 실제 4번 했어도 보상은 하루 2번까지만 | 설정 없음 |
| 활동별 보상 상한 | 해당 생활습관은 하루 최대 40분 | 설정 없음 |
| 자녀 전체 보상 상한 | 여러 생활습관 합쳐 하루 최대 몇 분/몇 원 | 설정 없음 |
| 패널티 횟수·상한 | 같은 종류 하루 몇 회, 총 몇 분까지 | 설정 없음 |
| 재전송 중복 방지 | 같은 확인 버튼을 다시 눌러도 1번 반영 | 구현되어 있으나 횟수 제한과 다른 기능 |
| 항목 입력 제한 | 보상 하나의 분 입력은 최대 240 | 구현되어 있으나 하루 총량 상한과 다름 |

**‘하루 한 행’은 중복 방지 단위이지 부모가 정한 하루 인정 횟수 정책이 아닙니다. ‘보상 하나 최대 240분’도 여러 활동을 합친 하루 최대량이 아닙니다.** 상한을 넘긴 수행은 기록을 없애지 않고 ‘수행 인정, 상한 초과로 추가 보상 없음’으로 남기는 편이 운영에 맞습니다.

## 5. 패널티 — 현재와 필요한 방식

| 운영 항목 | 현재 | 사용자가 요청한 공통 운영방식에 필요한 것 |
|---|---|---|
| 독립 패널티 등록 | 없음. Quest 하한 입력만 있음 | 보상과 같은 활동명·확인기준·측정·기간·횟수 폼에서 결과 방향을 패널티로 선택 |
| 패널티 종류 재사용 | 없음 | 종류를 한 번 등록하고 여러 규칙에서 참조 |
| 생활습관 발생형 패널티 | 직접 등록 불가 | ‘옷을 바닥에 둠’, ‘약속한 출발 시간 위반’ 등의 발생 사건을 종류별 기록 |
| 수량·구간형 패널티 | Quest 하한 후보만 있음 | 부모가 확인한 횟수/수치 구간과 명시적 차감 효과 연결 |
| 일·주 상한 | 없음 | 종류별 인정 횟수, 건당 차감, 기간 차감 상한 |
| 부모 승인 | 부모가 수치 확인하면 후보 표시 | 발생 확인과 차감 승인을 기록하고 원장 거래로 연결 |
| 미체크 | hold, 자동 패널티 아님 | 이 원칙 유지. 실제 문제 발생과 입력 누락을 구분 |
| 데일리 PASS 미달 | 스티커 0개, 자동 차감 없음 | 기존 스티커 자동 회수와 별도 패널티 발생을 혼동하지 않음 |
| 시간 차감 | 현재 실제 차감 없음 | 승인된 패널티만 원장에 음의 효과로 반영 |
| 정정 | 보상 권리는 보존하고 검토 표시 가능 | 패널티 원거래를 참조해 상쇄 거래 추가 |

보상과 패널티는 **같은 사건·측정·확인·제한 구조를 재사용**할 수 있습니다. 그러나 ‘음수 보상값을 입력하면 끝’은 아닙니다. 발생 사실과 차감 효과, 승인과 정정이 분리되어야 기존처럼 체크 누락 때문에 시간만 계속 빠지는 문제가 생기지 않습니다.

기존 시트의 패널티도 현재 유효·비활성 상태를 구별해야 합니다.

| 시트 조건 | 내용·효과 | 기간/횟수 | 현재 시트 상태 | 새 앱 대조 |
|---|---|---|---|---|
| P01 | 유인물 이틀 뒤 발견 -30분 | 하루 1 | 활성 | 독립 발생형 등록 없음 |
| P02 / 완화형 | 공부 미달 -80분 / 기탄 완료 시 -50분 | 하루 1 | **둘 다 비활성** | 부분 수행과 패널티 완화 관계 없음. 자동 부활시키지 않음 |
| P03 | 월 목표 미달 -600분 | 이벤트, 월 1회라는 메모 | 활성 | 월 목표 패널티 경로 없음. 현재 항목 240분 제한과도 다름 |
| P04 | 초과 사용분 ×3 | 하루 1 | 활성 | 실제 사용 원장·초과량 판정 없음 |
| P05 | 아침약 미복용 -180분 | 하루 1 | **비활성** | 약은 현재 확정 방향대로 보상·패널티에서 제외 |
| P06 | 응용 시험 50점 미만 -60분 | 이벤트 | 활성 | Quest 후보와 유사하나 실제 차감 원장 없음 |
| P07 | 10시까지 미취침 -90분 | 하루 1 | **비활성** | 발생형 시간 판정 없음. 자동 부활시키지 않음 |
| P08 | 주간 방정리 미이행 -180분 | 주 1 | 활성 | 주간 예정 여부·확인·차감 상한 경로 없음 |
| P09 | 토론 준비 미흡 -90분 | 주 1 | 활성 | 독립 체크리스트/구간 패널티 경로 없음 |
| P10 | 약속 위반 전액 몰수 | 이벤트 | 활성 | **과거에 문제로 지적한 정책. 복원 대상으로 삼지 않음** |
| P11 | 학교/학원 출발 시간 위반 -30분 | 하루 1 | 활성 | 독립 발생형 등록 없음 |
| P12 | 저녁약 시간 위반 -60분 | 하루 1 | **비활성** | 약은 계속 별도 기록 |
| P13 / P14 | 옷 방치 / 바닥 쓰레기 -30분 | 하루 1 | **둘 다 비활성** | 생활습관 발생형 예시는 참고하되 자동 활성화 안 함 |

이 표의 분량은 **과거 값**입니다. 특히 전액 몰수·초과 배수·약 패널티는 이미 바꿔 온 제품 방향과 충돌하므로 ‘시트에 있다’는 이유로 다시 넣으면 안 됩니다. 필요한 것은 과거의 **조건·기간·횟수 관계**를 회복하는 일이지 과거의 문제 정책을 전부 복제하는 일이 아닙니다. [1] [6]

## 6. 기존 원장과 새 원장이 연결해야 할 것

| 원장 항목 | 이전 시트에 있던 구조 | 현재 새 DB | 정리할 기준 |
|---|---|---|---|
| 출처 | `source_type`, `source_id`, `task_id` | 규칙·수행건·조건·보상 항목의 출처는 있음 | 원장 거래도 이 근거를 참조 |
| 거래 종류 | reward, penalty, usage, adjustment, forfeit 등 | 통합 거래 없음 | 보상/승인 차감/사용/취소/상쇄를 구별 |
| 실제 수행일 | `transaction_date` 및 task 로그의 사건 시각 | `business_date` 보존 | 횟수·상한은 입력한 날이 아니라 수행한 날 기준 |
| 입력·확인 시각 | `created_at`, `applied_at` 등 | 사건 입력과 부모 확인 시각 존재 | 소급 입력 순서와 수행일을 분리 |
| 잔액 효력일 | `effective_date` | 원장 효력 필드/실행 경로 없음 | 자정 확정과 늦은 확인의 다음 반영 규칙 필요 |
| 자산별 양 | `amount_minutes`, `cash_amount` | 강화물별 단위와 보상량 존재 | 분·원·서비스별 포인트를 따로 합산 |
| 처리 상태 | pending/applied 등 | 권리·이행 상태 존재 | 권리 상태와 원장 반영 상태를 혼동하지 않음 |
| 중복 방지 | `idempotency_key` | 사건·권리 중복 방지 존재 | 원장도 원천 사건별 중복 반영 차단 |
| 거래 후 잔액 | `balance_after` | 없음 | 원장 집계 또는 재생성 가능한 관측값 |
| 일별 화면 | 예정/반영/패널티/사용/마감잔액 스냅샷 | 정산 스냅샷 없음 | today 예정, hold, 승인 차감 대기, 사용 가능 잔액 분리 |
| 취소·소급 정정 | 과거에는 취소·상쇄가 부족했던 것으로 조사됨 | 확인 사건·보상 검토 이력 존재 | 기존 원장을 삭제하지 않고 상쇄와 새 거래로 정정 |

이전 시트에서도 정본이 충돌합니다. R01은 `03_nodes` 기본값 +80분이지만 조건표는 +60분이고, P08은 노드 기본값 -90분이지만 조건표는 -180분입니다. P13/P14 조건은 이름과 달리 `rule_id=RULE_P01`을 참조합니다. 시트 시간대는 `America/Los_Angeles`, 현재 가족은 `Asia/Seoul`입니다. 이러한 차이는 실제 운영일·트리거 기준을 확인해야 할 신호이며, 이번 조회만으로 모든 과거 실행의 오류를 다시 확정한 것은 아닙니다. [1]

## 7. 관계는 이 순서로 다시 고정하는 것이 맞다

**기존 구조를 버리는 전면 재개발보다, 지금 없는 운영 축을 분리해서 추가하는 편이 맞습니다.** 아래는 구현 완료표가 아니라 이번 확인에서 도출한 보완 구조입니다.

| 축 | 무엇을 정하는가 | 기존 자료 활용 | 필요한 보완 |
|---|---|---|---|
| 활동 | 학교생활·방정리·고양이 화장실 등 | 현재 활동/종류 ID 유지 | 같은 활동을 이름만 바꿔 중복 계산하지 않게 연결 |
| 내용 분류 | 공부·생활습관·기타 | 현재 category 유지 | 데일리/Quest와 분리 유지 |
| 수행 방식 | 데일리 / Quest, 발생형·반복형 | 기존 두 흐름 유지 | 하루 회차·발생 사건 슬롯 추가 |
| 측정 | 했음, 횟수, 점수, 백분율, 시각/소요시간 | 현재 측정 확장 | ‘3분 내 15개’처럼 복수 측정 조건을 구조화 |
| 결과 방향 | 보상 / 무효과 / 패널티 | 기존 판정 관계 활용 | 패널티도 독립 종류와 공통 등록 경로 |
| 종류·표식 | 공부 스티커·생활 스티커·패널티 표식 | 현재 그림 선택 유지 | 종류 ID, 아이콘, 합산 대상 관계를 따로 저장 |
| 제한 | 하루/주/월 최대 인정 횟수와 자산별 총량 | 시트의 scope/limit 개념 재사용 | 초과 수행은 기록하되 초과 보상은 막는 정책 |
| 조건·효과 | 해당 구간에 보상 1~2개 또는 승인 차감 | 현재 조건/강화물/보상 항목 재사용 | 음의 효과와 승인·상한 연결 |
| 사실·확인 | 자녀 보고, 부모 확인, 늦은 입력, 정정 | 기존 수행·액션 이력 유지 | 회차별 확인과 수행일 기준 상한 검사 |
| 정산·원장 | 무엇을 언제 사용 가능하게 반영하는가 | 기존 권리 출처 활용 | 불변 거래·자산별 잔액·사용·상쇄·정산 구현 |
| 잔차·스냅샷 | 모르는 사건과 그날 확정 상태 | 승인된 기존 원칙 유지 | 모르는 것은 hold, 임의 보상/패널티 추정 금지 |

중요한 반례는 세 가지입니다. 고양이 화장실을 하루 네 번 청소해도 하루 두 회까지만 보상한다면 네 번의 사실은 남고 두 회만 지급해야 합니다. 화요일에 월요일 기록을 입력해도 월요일 한도를 쓰며 화요일 한도를 차지하면 안 됩니다. 같은 생활습관의 세 번째 수행이 상한을 넘었다고 그 수행을 실패나 패널티로 바꾸면 안 됩니다.

패널티를 같은 방식으로 등록하더라도 부모 미확인과 실제 위반을 구별하는 원칙, 약 복용 별도 기록, 기존 원장 수정 대신 상쇄하는 방향은 유지해야 합니다. 초기 운영 규칙집의 제안 상한·기한은 전부 승인된 숫자가 아니므로 이번 보완에서 고정 기본값으로 몰래 넣지 않습니다. [6]

## 8. 현재 판단

| 질문 | 판단 |
|---|---|
| 지금 입력한 것을 다 버려야 하나? | **아니오.** 5개 게시 룰·강화물·실제 가족 연결을 보존하고 누락된 정책 관계를 추가하면 됨 |
| 화면만 수정하면 해결되나? | **아니오.** 하루 회차·최대 인정 횟수·패널티 종류·원장 반영은 DB와 판정 엔진의 문제 |
| 스티커가 종류별로 완전히 저장되어 있나? | 활동/룰과 그림 코드는 구별되지만, 독립 스티커 종류와 종류별 통합 집계는 미구현 |
| 패널티가 원래 운영과 같은 방식으로 되나? | 아니오. 현재는 Quest 하한 후보 중심이며 독립 패널티와 실제 차감 없음 |
| 현재 등록한 룰이 모두 자녀에게 작동하나? | 게시와 배정은 별개. 신버전 4개 미배정, 1개는 11/1 배정. 실제 수행/지급 운영 확인은 아직 필요 |
| 무엇부터 다시 정리해야 하나? | **측정 → 발생/회차 → 횟수·총량 제한 → 보상/패널티 효과 → 부모 확인 → 원장 반영**의 순서 |
