# Play Routine — 표 중심 부모 관리와 DB 확장성 검토

**현재는 난영님 한 명이 쓰는 부모 운영표로 단순화하는 것이 맞다. 상단 글자 메뉴로 업무를 바로 고르고, 자녀는 기존 카드·티켓·스티커 화면을 쓰면 된다. DB는 한 가족으로 축소하지 않고 가족별 관계·권한·원천 기록을 유지한다.** Grok-4.7도 이 방향을 조건부 채택으로 평가했다. 다만 표 화면을 만든다고 아직 없는 횟수 한도·법령 관계·원장·최고 구간 계산까지 완성되는 것은 아니다.[6] [7]

검토일은 2026-10-17이다. 현행 소스와 실DB 카탈로그를 읽기 전용으로 확인했고, 그 근거와 화면 제안을 xAI Grok-4.7에 실제로 보냈다. 코드·운영 데이터·권한·배포를 바꾸거나 초기화하지 않았다. 실제 자녀 기록·가족 식별자·이메일·비밀키는 그록에 보내지 않았다.

## 상단 메뉴와 표가 지금 더 적합한 이유

부모는 기능을 구경하는 것이 아니라 여러 규칙을 비교하고 누락·예외를 처리한다. 긴 입력 카드가 이어지는 화면보다 같은 열의 값을 비교하는 표가 이 일에 더 적합하다. 특히 처음부터 가족 선택·역할 선택·설정 안내를 매번 보여줄 필요가 없다. 부모 한 명, 기본 가족 하나, 기본 자녀가 정해져 있으면 해당 문맥을 유지한 채 운영을 시작하면 된다.

주신 참고 사이트를 실제 브라우저로 열어 상단 업무 메뉴, 하위 보기, 현재 위치 표시와 규정 목록 표를 확인했다. **가져올 것은 직접 경로 이동과 밀도 있는 표이지, 그 사이트의 여러 단 헤더·통계 카드 전체가 아니다.** Play Routine의 제안 상단 메뉴는 다음과 같다.[8]

```text
운영표  |  규정  |  보상·원장  |  강화물  |  설정·기록
```

상단 메뉴는 스크롤 중에도 접근 가능하게 두고 현재 위치를 표시한다. 각 메뉴는 독립된 직접 경로로 열리게 하며 새로고침·뒤로가기 때 선택한 보기를 복원한다. 메뉴를 누를 때마다 긴 같은 페이지의 아래쪽으로 스크롤시키는 방식은 피한다. 미저장 입력은 경고하거나 임시 보존하고, 이동만으로 인정·게시·지급을 처리하지 않는다.

‘규정’ 안에서는 기본법·공통 규율과 Task·Quest·Lifestyle, 개별 시행규칙을 구별한다. ‘운영표’ 안에서는 오늘·이번 주·밀린 확인을 보기 전환으로 둔다. 상단에 모든 유형·모든 주기·모든 설정을 나열할 필요는 없다. 경로가 몇 개 있느냐보다, 한 번의 이동으로 필요한 일만 보이고 입력 문맥이 유지되는지가 중요하다.

## 부모 운영표에서 편집할 것과 볼 것

일상 표의 행은 가능한 한 **특정 날짜의 특정 수행 회차 또는 사건**을 뜻해야 한다. 단순히 활동명 한 줄에 오늘 모든 사실을 덮어쓰면 같은 날 여러 번 수행한 생활습관을 기록할 수 없다. 하루에 여러 사건이 있으면 같은 활동 아래 회차를 펼치거나 발생 기록을 추가하는 구조가 필요하다.

기본 열은 날짜·번호/종류·활동·자녀 신고·부모 인정·인정 횟수/조건·결과·메모 정도로 압축한다. 자세한 시행 기준과 증빙은 선택한 행에서 펼친다. Task 완료, Quest 성적·소요시간, Lifestyle 발생·인정은 필요한 입력이 다르므로 모든 행을 하나의 점수 칸으로 통일하지 않는다.

표에서도 잔액·최종 지급액·누적 스티커·시행 버전은 자유 편집하면 안 된다. 부모가 입력하는 것은 수행 사실과 인정·정정·예외다. 계산 결과는 서버가 만든다. 예컨대 정상 PASS를 선택했다면 시스템이 구조화된 확인 사건과 기본 설명을 남길 수 있지만, 기존 RPC가 사유를 필수로 요구하므로 입력 축소에는 서버 계약 보완도 함께 필요하다.

표는 **엑셀처럼 다루는 화면이지, 실제 Excel/Google Sheets가 정본이나 계산 엔진인 구조가 아니다.** 수정 요청은 현재 인증된 RPC 또는 같은 검증을 갖춘 새 서버 계약으로 처리한다. 게시본과 과거 사건을 직접 UPDATE하거나 부모가 결과 금액 칸을 고쳐 원장을 덮어쓰게 해서는 안 된다. 현재 게시본·원천 사건의 불변성과 수정 번호 검사는 이 경계를 이미 보조한다.[4] [7]

선택 묶음 확인에서도 각 행의 원 수행일·주체·결과·수정 번호·재전송 방지 키는 남긴다. 저장 충돌이 나면 새 값을 다시 보여주고 재검토해야 한다. 서버에서 받은 최신 수정 번호만 붙여 부모 승인 없이 자동 재시도하면 다른 기기의 변경을 덮을 수 있다. 부모가 한 명이어도 자녀·휴대폰·다른 브라우저가 동시에 동작한다.[3]

한 화면에 월 31일, 모든 규정 전문, 모든 세부 측정 칸을 넣으면 세로 스크롤 대신 가로 스크롤이 생긴다. 기본은 오늘이나 이번 주로 제한하고 번호·활동명·표 머리글을 유지한다. 월간 Quest는 선택한 목표의 측정 근거와 결과를 펼친다. 표의 밀도를 높이는 것과 모든 정보를 동시에 노출하는 것은 다르다.

## 부모 표와 자녀 화면은 같은 DB를 사용한다

부모는 밀도 있는 운영표에서 사실을 확인하고, 아이는 자기 할 일·미확인 상태·스티커·보상권을 카드와 티켓으로 보면 된다. 두 화면에 별도 잔액·별도 사실 기록을 만들 필요가 없다. 같은 사건을 역할에 맞게 조회하고 각 역할이 허용된 동작만 수행한다.

현재도 자녀 본인과 부모를 검사하는 일별 루틴 조회, 자녀 신고, 부모 확인, 보상권 조회가 분리되어 있다. 부모 화면을 바꿔도 자녀 신고가 자동으로 부모 승인으로 바뀌어서는 안 된다. 조회 전용 보호자에게 부모 운영표의 수정 권한을 주는 것도 아니다.[4] [7]

다만 현재 구 활동과 신규 routine v2가 병존한다. 새 부모 표가 v2 조회만 가져오면 기존 활성 활동이 빠질 수 있다. 통합 조회는 출처를 구별해 보여주고, 같은 결과를 두 번 합산하지 않아야 한다. 기존 기록을 보존한다는 이유로 부모에게 구·신 양식 모두에 같은 내용을 입력하게 해서는 안 된다.

## 현 DB에서 유지할 확장 기반

실DB 카탈로그와 소스에서 가족·멤버십·자녀 프로필이 분리되어 있고, 관련 루틴의 `(객체 ID, family_id)` 복합 외래키가 존재함을 확인했다. 같은 가족에 속한 규칙·회차·조건·강화물·보상권을 연결하도록 DB 수준에서 제한하는 기반이다. 이는 다른 학부모가 각자 가족을 만드는 모델과 맞는다.[2] [4] [7]

루틴 raw table은 RLS가 켜져 있으면서 일반 클라이언트의 직접 읽기·쓰기 권한이 회수되어 있다. 필요한 인증 RPC만 열려 있고, RPC 안에서 부모 또는 해당 자녀 본인을 확인한다. 따라서 ‘표로 바꾸려면 테이블 직접 수정 권한을 줘야 한다’는 주장은 틀리다. 현재의 RPC 경계를 재사용하는 편이 낫다.[1] [7]

규칙 계보와 불변 게시본, 강화물 이름·단위·조건 금액의 스냅샷, 수행 projection과 원천 사건, 보상권과 실제 이행의 분리도 유지할 가치가 있다. 현재 가족·자녀·날짜 조회 인덱스와 중복 발생·지급을 막는 유일 키도 존재한다. 다만 이것은 제약과 인덱스의 존재 확인이며 몇 가족을 어떤 속도로 지원하는지 측정한 결과는 아니다.[4] [7]

**그러므로 DB를 버리거나 가족마다 새 DB를 만들 이유는 없다. 가족별 데이터와 권한 기반은 재사용하고, 현재 빠진 정책 관계와 조회 계약을 보완하는 방향이 맞다.**

## 그록과 확인한 실제 보완점

### 1. 새 법령과 정책을 표현하는 구조는 아직 부족하다

현재 `routine_flow`는 DAILY/QUEST이고, 규칙·조건·배정은 존재하지만 기본법→세 하위규정→개별 시행규칙의 정확한 버전 관계, 호환 검토, 월별 채택 목록은 아직 별도 구현 대상이다. 최신 법령형 v0.2는 검토 설계이지 현행 migration이 아니다.[4] [6]

Lifestyle 하루 3회 같은 조건은 화면만으로 해결할 수 없다. 현행 v2 발생 건의 유일 키는 `(assignment_id, business_date)`이며 스티커는 0~2개다. 이는 하루 여러 회의 생활습관 발생·인정 횟수를 별도로 관리하는 모델과 다르다. **발생 회차와 인정 횟수·보상량 한도를 분리하는 증분 설계**가 필요하다. 횟수를 칭찬 스티커 숫자에 넣어 우회해서는 안 된다.[4]

Quest의 실제 측정도 단일 0~100 숫자 구조만으로는 ‘정답 개수와 소요시간을 동시에 충족’ 같은 조건을 완전히 설명하지 못한다. 현재 시간 보상 항목에는 240분 상한이 있어 300분·480분·600분 보상을 지원한다고 할 수 없다. 큰 금액을 저장하려고 임의로 여러 보상권으로 쪼개는 대신, 승인된 정책에 맞춰 입력·효과 처리 계약과 제약을 개정해야 한다.[4]

### 2. 최고 구간 최종총액형 보상은 현재 발행 방식과 다르다

그록은 현재 기간 마감·Quest 발행 코드가 달성한 tier들을 모두 보상권으로 만든다는 점을 지적했다. 이것은 **추가 보상이 독립적으로 누적되는 조건**에는 가능한 방식이지만, 학교 규칙처럼 최고 구간의 최종 총액만 인정하는 경우에는 그대로 쓸 수 없다.[4] [6]

학교 규칙의 5~7개 10,000원과 8개 이상 15,000원을 각각 달성 보상권으로 발행하면 총 25,000원이 되어 확정한 정책과 달라진다. 이미 유효 보상권 10,000원이 있다면 추가 발행은 5,000원이고, 실제 이행 계산은 이미 제공한 액수와 별도로 연결한다. 누적형과 최고총액형을 명시적으로 구별하고 적용 기간·정정·중복 방지 계약을 구현해야 한다. 기존 권리나 이미 제공한 보상을 이번 검토를 이유로 바꾸거나 삭제하지 않는다.

현재 마감은 확인된 스티커 합계를 사용하지만 예정 회차 전체의 미확인 완결성 검사가 부족하다. 새 운영표가 이를 정상 최종 마감으로 감싸면 안 된다. 미확인은 0개가 아니며, 최종총액 계산과 미확인 보류를 서버에서 먼저 보완해야 한다.[4] [6]

### 3. 새 부모 표에는 범위가 제한된 조회가 필요하다

현재 규칙·배정·보상권 목록은 가족 또는 자녀의 전체 이력을 JSON으로 모아 반환하며 페이지/기간 제한이 없다. 부모와 자녀의 갱신 경로도 전체 보상권을 조회한다. 지금 행이 적다고 해도 변경 이력과 사건이 계속 쌓이면 부담이 늘 수 있다.[7]

새 표에는 가족·선택 자녀·날짜/주·상태와 페이지 또는 커서 범위를 명시한다. 주간 표를 만들기 위해 하루 조회를 반복 호출하면 왕복이 늘 수 있으므로 필요한 주간 조회·요약 계약을 설계한다. ‘목록 일부만 클라이언트에서 숨기기’는 서버 조회량을 줄이지 않는다. 추가 인덱스·캐시·파티션은 실제 쿼리 계획과 부하를 측정한 뒤 결정한다.

### 4. 한 가족을 기본 선택하되 서버 권한을 생략하면 안 된다

현재 부모 화면은 멤버십의 첫 부모 역할을 선택한다. CSV도 명시 가족 선택이 없으면 한 가족을 선택하는 경로가 있다. 난영님이 한 가족을 운영할 때는 단순한 기본값이지만, 같은 계정이 여러 가족을 관리하게 되면 명시적 전환과 선택 범위의 보존이 필요하다.[5] [7]

처음부터 가족 전환 UI를 크게 만들 필요는 없다. 다만 모든 표 요청과 캐시의 가족·자녀·날짜 범위는 지금부터 일관되게 유지해야 한다. URL이나 브라우저의 선택은 힌트이고 서버가 멤버십과 대상 가족을 재검증한다. 날짜·보기 필터는 직접 경로에 둘 수 있지만 인증 토큰·자녀 이름·복약 내용은 넣지 않는다.

서버 PostgreSQL 연결 역할은 카탈로그상 RLS를 우회하는 `postgres`였다. 현재 초대·CSV·아바타 경로는 역할·가족 검사로 접근을 제한하지만, 새 표 API를 추가할 때 RLS가 모든 것을 막아 준다고 가정하면 안 된다. 예컨대 아바타는 선행 권한 조회 후 UPDATE에 profile ID만 사용하므로 같은 문장에서 가족과 활성 권한까지 확인하는 방어를 보강할 수 있다. 이는 현재 데이터 유출이 확인됐다는 뜻이 아니라 앞으로의 서버 SQL에 지켜야 할 경계다.[1] [7]

### 5. 감사 표와 민감 기록은 운영표에 무조건 합치지 않는다

현재 `routine_request_events`에는 actor와 재전송 키·요청/응답은 있지만 가족 전용 열은 없다. 지금은 내부 감사 표이며 가족별 일반 조회 경로가 확인되지 않았다. 이를 그대로 부모의 범용 ‘원장’으로 공개하지 않는다. 향후 가족별 감사 목록이 필요하면 기존 불변 행을 덮지 않고 가족 범위가 명확한 조회 projection을 추가한다.[4] [7]

복약 구조화 기록과 양육일기는 별도 민감 접근범위가 필요하다. 현재 보호자 조회 전용 역할이 있다고 해서 아직 구현하지 않은 복약 테이블의 비공개까지 검증된 것은 아니다. 다른 가족이나 일반 보호자 상태창에 자동 노출하지 않는다. 이행과 보상권도 실제 원장 잔액이 아니므로 원장 메뉴를 만들더라도 ‘0원/0분’으로 완성된 기능처럼 채우면 안 된다.

## 다른 학부모로 확장할 때 공유할 것

공유할 것은 아이의 일지나 가족의 잔액이 아니라 **승인된 기본 규범·템플릿의 버전**이다. 각 가족은 그 버전을 채택하고 자기 강화물·금액·한도·일정·부모 재량을 적용한다. 가족 A의 설정 변경으로 가족 B의 과거 평가와 보상이 바뀌어서는 안 된다.

따라서 미래에는 ‘공통 규범/템플릿의 정체성과 버전’과 ‘가족의 채택·개정·월별 계획’을 구별한다. 가족별 강화물 카탈로그와 수행·확인·보상권은 가족 안에 둔다. 공동 템플릿이 있다는 이유로 한 가지 금액·스티커·약속을 모든 가족에 강제하지 않는다.

기존 DB의 가족별 관계를 제거하지 않으면 두 번째 부모의 가족은 같은 PostgreSQL에 독립된 행으로 추가하는 방향을 유지할 수 있다. 다만 새 모집 전에 다른 가족 ID 조작, 자녀·보호자 승인 거절, 연결 종료 후 접근, 가족 전환 뒤 캐시 섞임, 재시도·동시 확인의 회귀를 실제로 시험해야 한다. 이번 검토는 카탈로그와 코드 검토이며 성능·실제 다중 가족 운영 부하 시험까지 수행한 것은 아니다.

## 지금 필요한 것과 미뤄도 되는 것

지금 필요한 것은 상단 업무 메뉴, 오늘/주간 중심 운영표, 필요한 행만 펼치는 입력, 범위가 제한된 조회, 정상 PASS 입력 축소, 가족·revision·멱등성 경계다. 확정한 Lifestyle·Quest·학교 최종총액 규칙을 실제로 운영하려면 해당 관계와 처리기를 보완하는 작업도 필요하다. 이것은 미래 대규모 확장 대비가 아니라 **현재 규칙을 올바르게 표현하기 위한 기능**이다.

반대로 가족마다 새 DB·새 스키마·새 테이블을 만들거나, 화면 메뉴마다 테이블을 추가하거나, 그래프 DB·마이크로서비스·대규모 분할을 지금 도입할 이유는 없다. 사용자 한 명일 때 그런 구조는 부모 화면 문제를 해결하지 못하고 운영 복잡성만 늘릴 수 있다. 표 UI의 이점도 실제 난영님 입력으로 확인해야 하므로 스크롤 감소율이나 처리 속도 배율을 약속하지 않는다.

**채택할 방향은 ‘난영님용 표 관리자 + 고정 상단 메뉴 + 아이용 카드 화면 + 가족별 관계형 DB’다. DB 격리의 기반은 유지하고, 계산·법령·횟수·기간 관계의 부족을 증분 보완한다. 화면 단순화와 아직 없는 정책 구현을 같은 완료 상태로 표시하지 않는 것이 핵심이다.**
