# Play Routine 부모 관리 프로세스 과잉 검토

**검토일: 2026-10-17**

## 결론

**과한 것은 관계형 기록과 개정 이력 자체가 아니라, 시스템 내부의 처리 단계를 부모의 반복 입력·탐색·확인 작업으로 너무 많이 노출한 점이다.** 부모는 아이의 사실과 예외를 판단해야 하지만, 매번 설명문을 작성하고 같은 결과를 여러 화면에서 찾아 관리할 필요는 없다.

가장 먼저 줄일 것은 **정상 PASS의 자유 서술 의무**, **일상 화면에 노출된 규칙 작성·배정 폼**, **저장 후 게시를 위해 초안 목록으로 다시 내려가는 동선**이다. 그다음 보상 현황과 밀린 확인을 한곳에서 처리한다.

이번 검토는 현행 소스와 법령형 설계 문서를 읽기 전용으로 대조했다. 실제 부모 로그인·입력 시험, 운영 데이터 전수 조회, 코드 변경, DB 초기화, GitHub 게시를 실행하지 않았다. 최신 법령형 구조 v0.2와 기본법·하위규정 v0.6은 아직 운영 UI·DB에 적용되지 않은 검토 문서이며, 아래 개선안도 현재 기능이 아니다.

## 1. 현재 과한 부분과 줄이는 방법

| 우선순위 | 현행 과정·화면 | 판단 | 축소안 | 유지할 것 |
|---|---|---|---|---|
| 1 | 일반적인 데일리 PASS도 결과 선택 → 확인 이유 작성 → 확인 기록 저장 | **반복 서술이 과함.** 평범한 완료 확인에 매번 글을 쓰게 한다. | 정상 PASS는 명시적 확인 버튼과 기본 설명으로 기록. 메모는 선택. 차감 승인·정정·분쟁은 사유 필수. | 부모의 실제 인정, 확인자·시각·대상·결과, 자녀가 볼 설명 |
| 1 | 룰 등록기·새 배정·보상 권리·현재 배정·수동 보상이 한 부모 화면에 길게 이어짐 | **설정과 일상 운영이 섞임.** 이미 설정을 끝낸 부모도 설정 양식을 지나가야 한다. | 기본 화면은 ‘오늘 확인·밀린 확인·줄 보상’. 규칙·배정·강화물·가족·내려받기는 설정으로 이동. | 설정 접근성과 기존 기록 조회 |
| 1 | 검토 화면에서 저장 → 아래 초안 목록으로 이동 → 같은 초안 게시 | **저장본 보존은 필요하지만 왕복 동선은 불필요.** | 검토 화면 안에서 저장본 요약과 최종 게시를 완료. 다른 초안 목록은 이어쓰기 용도로 유지. | 게시 전 저장본 검증, 부모의 최종 게시 결정, 효력일·버전 고정 |
| 2 | 자녀·수행일을 바꾸어 항목마다 확인. 확인이 밀리면 날짜별로 반복 탐색 | **부모가 밀렸을 때 복구 비용이 큼.** | ‘미확인 전체’에서 날짜·자녀·종류별 묶음 표시. 부모가 실제 확인한 항목만 선택하여 일괄 인정. | 항목별 원 수행일·개별 확인 사건. 미선택 항목은 미확인 유지 |
| 2 | 수행 확인 뒤 기간 마감, 보상권마다 이행 표시 | **서로 다른 의미는 필요.** 그러나 집계·항목 탐색·클릭은 줄일 수 있음. | 기간별 집계와 마감 대기 목록을 시스템이 준비. 실제 함께 제공한 보상은 선택 묶음으로 이행 표시. | 미확인 완결성 검사, 실제 외부 제공 확인, 단위별·항목별 기록 |
| 2 | 규칙에서 나온 보상권과 별도 주간 돈·기간 돈·보너스 쿠폰을 다른 양식에서 관리 | **같은 보상을 두 번 입력해야 하는 것은 아니나, 어느 양식을 쓸지 부모가 판단해야 함.** | ‘보상 현황’ 진입점 통합. 출처를 ‘규칙 달성 / 부모 특별보너스 / 기존 기록’으로 표시. 규칙 보상은 재입력하지 않도록 안내. | 수동 보너스의 독립성, 금전·시간·포인트·약속의 구별 |
| 2 | 활동 이름과 아이 표시 키워드, 조건 이름, 비교 연산, 스티커 아이콘 등 범용 필드가 함께 노출 | **간단한 규칙에도 설계자 수준 선택을 요구함.** | Task·Quest·Lifestyle과 해당 방식의 양식을 먼저 고르고 관련 필드만 표시. 이름 재사용·조건 기본명·선택 아이콘 등은 보조 기능으로 둠. | 실제 기준·단위·한도·중립·차감 경계는 명시. 미정 값을 자동 확정하지 않음 |
| 3 | 기존 규칙 영역은 ‘기록 보존’으로 접혀 있지만 안에 새 등록·게시·배정도 가능한 컴포넌트가 남음 | **보존과 계속 운영을 혼동하기 쉬움.** | 이력 조회와 기존 활성 활동의 필요한 확인은 유지. 신규 생성 경로는 정리. 새 체계 전환은 별도 승인 후 적용. | 이미 활성인 구버전 활동·미확인 기록·보상권을 임의 폐기하지 않음 |
| 3 | 상단 ‘열린 잔차’ 카드가 연결 전인데 기본 화면을 차지함 | **미구현 상태를 매일 설명하는 정보는 운영에 도움이 적음.** | 일반 부모 홈에서는 제외. 실제로 해결 질문이 생겼을 때 ‘규칙 확인 필요’로 노출. | 잔차의 개념·원사건·결정 이력. 미확인과 잔차를 구별 |

**정정:** 단계별 임시저장은 현재 필수가 아니다. 저장 없이 ‘다음/이전’ 이동이 가능하다. 세 단계를 유지하는 것 자체보다 **게시 버튼의 위치와 저장·게시의 연결**이 문제다.

## 2. 줄이면 안 되는 부분

| 구분 | 유지 이유 | 부모에게 최소한으로 보일 형태 |
|---|---|---|
| 실제 부모 확인 | 자녀 자기보고를 승인된 수행 사실로 자동 바꿀 수 없음 | ‘인정 / 아직 인정하지 않음’ 또는 실제 측정값 입력 |
| 차감 승인·정정 사유 | 아이가 결과를 이해하고 과거 보상 변경을 추적할 수 있어야 함 | 해당 상황에서만 사유 칸 열기 |
| 시행일·버전·개정 이력 | 오늘 바꾼 금액으로 과거를 다시 계산하면 안 됨 | 변경 전후 요약과 적용 시점. 상세 이력은 펼치기 |
| 미확인·중립·한도 초과 구별 | ‘아직 안 봄’과 ‘확인했지만 보상 없음’은 다름 | 이해 가능한 상태명. 내부 상태코드는 숨김 |
| 발생 보상권과 실제 제공 구별 | 달성했다고 현금 송금·충전·체험 제공까지 된 것은 아님 | ‘받을 보상 / 제공 완료’ 구별 |
| 자산별 기록과 중복 방지 | 시간·원·포인트 합산 또는 같은 기간 이중 지급 방지 | 사용자에게는 종류별 금액, 내부에는 고유 키·원천 연결 |
| 가족별 권한 | 자녀·조회 전용 보호자가 부모 승인을 대신할 수 없음 | 역할에 맞는 버튼만 표시 |

**로그가 필요하다는 이유로 글쓰기를 강제할 필요는 없다.** 정상 PASS를 부모가 명시적으로 눌렀다면 ‘부모가 수행을 인정함’이라는 설명과 구조화된 사건을 시스템이 남길 수 있다. 직접 관찰했는지, 교사 연락을 받았는지 등 부모가 선택하지 않은 근거를 시스템이 지어내서는 안 된다.

## 3. 실제 규칙에 적용하면

| 사용자 규칙 | 부모가 판단·입력할 것 | 시스템이 담당할 것 | 없애야 할 반복 작업 |
|---|---|---|---|
| 밀크티 일 Task | 해당 수행을 인정할지 확인 | 당시 규칙의 40분 보상 효과·원천 기록 준비 | 매일 ‘40분’과 같은 정상 사유를 다시 입력 |
| 학교 주간 Task | 일별 문제없음/문제 있음, 해당 규칙이 허용하는 교사 칭찬 확인 | 학교 종류만 집계하여 0~4개 없음 / 5~7개 10,000원 / 8개 이상 최종총액 15,000원 계산 | 같은 스티커 수와 주간 금액을 수동 돈 양식에 다시 기입 |
| 횟수 제한 Lifestyle | 발생한 수행을 인정할지 확인 | 수행·인정 횟수를 따로 기록하고 규칙에 정한 하루 한도 적용 | 부모가 별도 표로 오늘 몇 번 보상했는지 계산 |
| 기탄수학 월간 Quest | 시행령이 요구한 실제 정답 수·소요시간 등 측정 근거 | 복수 조건 판정과 300분·현금 50,000원의 독립 효과 준비 | 같은 사실을 시간 보상과 현금 보상에 각각 다시 입력 |
| 별도 특별보너스 | 재량 발행 여부와 종류·수량, 필요한 짧은 메모 | 별도 발행 사건과 실제 사용 상태 | 일반 Task·Quest의 새 시행령을 보너스 한 번 때문에 새로 작성 |
| 생활습관 차감 사건 | 실제 위반 사실과 차감 승인·사유 | 승인된 횟수·차감량·상한·정정 관계 적용 | 미체크를 자동 위반으로 바꾸거나 부모가 직접 잔액 계산 |

이 표의 ‘시스템 담당’은 새 규정 체계 구현 목표다. **현재 앱에 일일 횟수 한도·복수 측정 Quest·최종총액형 학교 보상·자동 원장 정산이 모두 완성됐다는 뜻이 아니다.** 확정된 보상값은 바꾸지 않고, 계산·기록의 담당만 부모에서 시스템으로 옮기는 제안이다.

## 4. 권장하는 부모의 최소 프로세스

| 시점 | 부모 작업 | 시스템 작업 |
|---|---|---|
| 처음 시작 | 자녀 연결, 사용할 강화물 준비, 첫 운영계획 승인 | 연결·권한 검증, 규칙/강화물 버전 고정 |
| 월별 준비 | 지난 계획을 보며 바뀐 것만 유지·개정·제외·신설 결정 | 계속 유효한 항목 제안, 종료 이벤트·일정 충돌·미정 항목 표시 |
| 평소 | 오늘 또는 밀린 항목의 사실 확인 | 기록·한도 사용·집계·효과 후보 계산 |
| 주·월 종료 | 해결이 필요한 미확인·분쟁·예외 검토, 승인된 운영 방식에 따른 마감 결정 | 완결성 검사와 기간 요약, 중복 없는 권리 산출 |
| 실제 보상 제공 | 실제 함께 제공한 항목만 선택해 완료 표시 | 각 보상권의 개별 이행 기록 |
| 문제가 생겼을 때 | 정정·차감·예외의 사유와 처리 결정 | 원기록 보존, 상쇄/후속 효과, 영향 목록 |

기본 부모 화면은 **오늘 확인 / 밀린 확인 / 줄 보상**이 중심이면 충분하다. 규정 작성·배정·강화물·가족·내려받기·개정 이력은 별도 관리 영역에서 필요할 때 연다. Task·Quest·Lifestyle은 이 화면 안의 분류로 사용하되, 서로 다른 인정 방식을 같은 점수 입력 칸으로 통일하지 않는다.

## 5. 법령형 체계가 과도한 행정으로 커지지 않게 할 경계

| 설계 요소 | 필요한 용도 | 과해지는 사용법 | 권고 |
|---|---|---|---|
| Manus → Grok → 사용자 검증 | 초기 규정·개정·호환·전환의 검토 | 매일 PASS와 쿠폰 사용마다 AI 승인을 기다림 | 규정 검토와 일상 사건 처리를 분리. 확정한 검증 절차는 유지하되 여러 개정을 변경 묶음으로 검토 |
| 월별 운영계획 | 정확한 규칙 버전과 일정 채택 | 변하지 않은 생활습관·강화물을 매월 다시 등록 | 같은 정본 참조, 바뀐 항목 중심 검토 |
| 법령 번호·버전·호환 연결 | 변경 이력과 결과 설명 | 부모가 매번 ID·버전·부모 규정 링크를 직접 입력 | 시스템 부여·연결, 부모는 의미와 변경점을 승인 |
| 잔차 | 기존 규정으로 해결할 수 없는 질문 | 미체크·중립·한도 초과를 매번 새 잔차 사건으로 심사 | 정상 상태는 자동 분류, 규정의 진짜 공백·충돌만 질문으로 노출 |
| 지급·정산 기록 | 발생권·사용 가능량·실제 제공을 구별 | 같은 확인을 이름만 바꾸어 여러 화면에서 요구 | 내부 층은 유지, 부모 작업은 의미가 다른 결정만 노출 |

현재 앱에는 Grok 검토 버튼·RPC가 연결되어 있지 않다. 위 AI 경계는 현재 반복 부담의 지적이 아니라 **새 법령형 체계를 구현할 때 생길 수 있는 과잉을 예방하는 제안**이다.

## 6. 자동화보다 먼저 보완할 안전점

현재 `confirm_routine_period` 소스는 확인된 회차를 합산하지만, 해당 기간에 예정된 회차 전체의 미확인 여부를 검사하는 완결성 조건이 충분히 드러나지 않는다. 이것은 실제 지급 오류가 발생했다는 증거가 아니라 **마감 자동화 전에 확인·보완할 서버 계약**이다.

따라서 ‘부모가 버튼을 덜 누르게 하자’는 이유로 곧바로 자동 최종 마감하면 안 된다. 미확인이 있으면 최종 마감은 보류하고, 확정된 내용과 해결 대기를 구별해야 한다. 기간 경계·중간 지급·마감 방식은 최신 문서에서도 추가 운영 명세로 남아 있으므로 새 정책을 임의 확정하지 않는다.

정상 PASS의 입력을 줄이는 개선도 UI에서 필수 표시만 지우는 것으로 끝나지 않는다. 현 DB·RPC가 자유 텍스트 사유를 필수로 요구하므로, 구조화된 기본 설명과 예외 사유를 구별하는 계약을 함께 보완해야 한다.

## 7. 적용 순서 제안

1. **일상/설정 화면 분리와 정상 PASS 서술 의무 축소.** 가장 자주 하는 작업부터 줄인다.
2. **미확인 모아보기와 현재 초안에서 직접 게시.** 밀린 작업·설정 왕복을 줄인다.
3. **보상 현황의 출처별 통합과 실제 제공의 선택 묶음 처리.** 데이터 층은 합치지 않는다.
4. **기간 마감 완결성 보완 후 집계·마감의 자동화 범위를 확정.** 사용자 승인 없는 자동 마감·실제 지급은 하지 않는다.
5. **월별 승계·개정 묶음을 새 법령형 구조에 연결.** 매달 재등록을 만드는 대신 정확한 버전 참조를 유지한다.
