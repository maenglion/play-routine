# Manus 1차 검토 — 한 가족용 표 UI와 여러 가족용 DB

현재 운영자는 부모 한 명으로 가정하되 로그인·가족·자녀·보호자 역할과 가족별 데이터 경계는 유지한다. 한 명이라는 사실은 기본 화면을 단순하게 만드는 조건이며 DB를 한 가족 데이터로 하드코딩하거나 부모를 시스템 전체 관리자 권한으로 바꾸는 이유가 아니다.

부모 화면은 엑셀 같은 조회·입력 격자로 재구성할 수 있다. 실제 Excel/Google Sheets를 데이터 정본이나 계산 엔진으로 다시 쓰는 것은 아니다. 오늘 운영표와 주간 검토, 규정/강화물 설정은 같은 작업공간의 보기 전환으로 두되 모든 설정 폼을 세로로 이어 붙이지 않는다. 이름과 기준은 고정 표시하고, 선택한 날짜·기간과 Task/Quest/Lifestyle에 필요한 입력만 펼친다. 한 화면에 월 31일과 모든 상세 조건을 몰아넣으면 가로 스크롤이 늘므로 주간 또는 날짜 범위를 기본으로 삼는다.

표의 일상 입력은 수행 신고·부모 인정·사유·실제 측정값/발생 사실이다. 잔액·최종 지급액·시행 버전·자동 계산된 스티커 합계는 결과 칸이며 자유 편집하지 않는다. 일괄 입력은 부모가 실제 확인한 행만 승인하며 서버에 각각의 사건과 revision/idempotency를 남긴다. 부모 하나라도 여러 탭·휴대폰·자녀 동시에 동작하므로 동시성 보호는 남긴다. 행의 이름이나 아이콘이 아니라 원천 규칙/회차 식별자로 연결한다.

자녀는 같은 사실과 규칙을 카드/티켓/스티커 형태로 본다. 부모와 자녀의 화면은 달라도 DB를 각각 만들지 않는다. 복약 구조화기록과 선택 양육일기는 민감한 별도 접근범위로 유지하고 일반 보호자 상태창에 무조건 노출하지 않는다.

현재 routine v2에는 가족별 복합 FK, 규칙 버전 계보, 불변 게시본, 강화물 효과 snapshot, 원천 수행·부모 확인 이벤트, 보상권, actor/key 중복 방지가 존재한다. 초기 스키마는 families/memberships/child_profiles로 다중 가족을 표현하고 guardian은 조회 전용 경로다. 이는 재사용할 기반이다. 다만 최신 Task/Quest/Lifestyle 법령 위계·월별 승인 묶음·Lifestyle 하루 여러 회차/인정 한도·복수 측정·자정 불변 원장·최고 구간 최종총액형 보상은 문서상 계획을 현행 구현 완료라고 할 수 없다.

가족별 강화물 카탈로그는 집마다 이름/단위/보상 정책이 달라야 하므로 유지한다. 다음 가족을 추가할 때 공유할 것은 개인 기록이 아니라 기본법/템플릿의 승인된 버전이다. 공유 규범과 가족별 채택·개정·강화물·운영계획은 구별하고, 가족 A의 상위 규범 수정이 가족 B의 과거 보상을 바꾸면 안 된다.

대규모 운영을 이유로 지금 가족마다 별도 DB/테이블·새 그래프 DB·마이크로서비스·파티션을 도입하지 않는다. 처음은 공유 PostgreSQL+가족 경계가 적합하다. 앞으로 다른 학부모를 초대하기 전에 잘못된 가족 ID, 부모/자녀/보호자 권한, 캐시 키의 family/child/date 범위, 탈퇴·연결 종료 후 접근, DB 운영자 경로·서버 RPC 권한을 실제 테스트해야 한다. 사용자 수가 늘면 기간·건수 제한·요약조회·쿼리 계획/잠금 대기부터 측정한다. 처리 가능한 가족 수나 성능 개선률을 측정 없이 약속하지 않는다.

검토 제안이며 UI·DB를 변경하거나 초기화하지 않았다.

## 사용자 추가 지시 — 2026-10-17 21:30

화려한 디자인보다 고정된 상단 글자 메뉴와 직접 경로 이동이 중요하다. 참고 링크는 https://letscheck-sinbo.netlify.app/regulations?scope=master 이다. 읽기 전용 추출에서 상단 ‘데이터 수집 및 활용목적 / 검증 방법론 / 기술 사양’의 직접 경로 링크, 현재 위치 표시, 표 중심 규정 목록을 확인했다. 이 사이트의 업무나 데이터 구조를 Play Routine으로 가져오는 것이 아니라 탐색 방식을 참고한다.

제안 상단 메뉴는 ‘운영표 | 규정 | 보상·원장 | 강화물 | 설정·기록’이다. 부모용 메뉴는 스크롤해도 접근 가능하게 두고 현재 선택을 표시한다. 규정 안에서 Task·Quest·Lifestyle을 번호·유형별로 고르며 운영표의 오늘/이번주/미확인은 보기 전환으로 처리한다. 긴 한 페이지의 앵커 이동만 만들지 않고 각 메뉴는 직접 URL로 열고 뒤로가기·새로고침 후에도 가족·자녀·기간 선택을 안전하게 복원한다. 이름·날짜·종류·선택 보기 등은 URL에 둘 수 있으나 개인정보·인증 토큰은 넣지 않는다. 부모 화면에서 다른 메뉴로 옮겨도 미저장 입력은 경고 또는 임시 보존하고, 이동만으로 규칙을 게시하거나 부모 승인·보상 지급을 하지 않는다.

상단 메뉴를 늘린다고 DB 엔티티나 물리 테이블을 메뉴별로 새로 만드는 것은 아니다. 메뉴는 같은 가족 범위의 업무 보기이고, 역할별 승인과 실제 기록 구조는 서버에 남는다. 현재 원장 메뉴는 미구현 부분을 0원/0분인 완성 기능으로 보여주지 않고 보상권과 실제 원장 상태를 분명히 구별해야 한다.

## 추가 확인 근거

참고 사이트를 실제 브라우저로 열어 상단 업무 메뉴 ‘규정·법령 / 부서별 통계 / 사업별 통계 / 잔차 데이터’와 하위 보기 ‘내부규정 / 사규예고 / 전체 게시물’, 현재 위치 표시, 표 목록을 확인했다. Play Routine도 상단 업무 메뉴와 해당 업무 안의 하위 보기를 구별하는 구조가 적합하다. 참고 사이트의 다단 헤더 전체 높이나 통계 카드를 복제할 필요는 없다.

현재 Home.tsx:98은 멤버십에서 첫 OWNER_PARENT/PARENT를 find하여 해당 가족의 자녀를 조회한다. 사용자 한 가족에서는 단순한 기본값이지만, 동일 부모가 여러 가족을 관리하는 경우 명시적 가족 선택과 선택 범위별 캐시가 추가로 필요하다. 다른 부모들이 각자 한 가족을 쓰는 확장과 한 부모가 여러 가족을 관리하는 확장은 같은 요구가 아니다.

공식 근거: https://www.postgresql.org/docs/current/ddl-rowsecurity.html 는 테이블 소유자/BYPASSRLS와 권한 함수 경계를 구별하고, https://www.postgresql.org/docs/current/ddl-constraints.html 는 복합 외래키의 같은 행 연결과 CHECK의 다른 행 누계 제한을 설명한다. https://www.postgresql.org/docs/current/explicit-locking.html 는 다중 행 잠금 순서·트랜잭션 범위 잠금·교착 관리 기준이다. 이번 검토는 기존 테이블을 강제로 직접 편집하게 허용하거나 RLS만으로 모든 경로의 보안을 보증하지 않는다.
