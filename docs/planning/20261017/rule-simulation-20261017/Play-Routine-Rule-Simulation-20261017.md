# Play Routine — 이전·새 조건 대입 실행 결과

**판정·한도·권리·정산을 테스트 어댑터로 실행했습니다. 46개 시나리오, 독립 확인 246/246개 통과입니다.**

**운영 Supabase·자녀 계정·활동 배정·실제 지급·배포는 바꾸지 않았습니다.** 실제 수행 기록이 아니라 요청하신 가정 입력입니다. 새 조건은 2026-10-16 보존 조회 5룰이며 오늘의 DB를 재조회한 것은 아닙니다.

## 1. 먼저 볼 결론

하루 여러 회차와 인정 횟수, 기본/추가 구간, 돈+시간 두 효과, 부모 확인과 차감 승인, 소급 귀속일과 효력일을 서로 다른 관계로 저장해 시험했습니다. 같은 그림을 선택해도 스티커 종류 ID로 합산 대상을 구분합니다.

이 합계는 실제 보상 예산이 아니라 해당 시험 입력의 실행값입니다. 시간과 서비스 포인트를 원화·한 계정 잔액으로 섞지 않았습니다. 기존 네 룰의 미배정을 운영에 추가하지 않고 테스트 가족에만 임시 배정했습니다.

| 통합 예시의 시점 | 이미 효력이 생긴 시간 | 시간 권리 누적 | 외부 포인트 |
|---|---:|---:|---:|
| 금요일 자정 전 | 440분 | 640분 | 실제 이행 0 / 권리 45,000 |
| 모든 기본·추가 권리의 이행 완료 | 640분 | 640분 | 실제 이행 45,000 / 권리 45,000 |

**오늘 예정과 이미 보유한 것을 나눠야 하는 이유:** 금요일 확인 직후에는 아직 다음 자정에 반영할 분이 있으며, 외부 포인트도 달성권과 지급 확인은 다른 단계입니다.

## 5. 추가 한도 선택에 따라 결과가 달라집니다

| 비교 | 전체 조건만 인정 | 자산별 부분 인정 |
|---|---:|---:|
| 밀크티40분+기탄40분, 시험용하루합산60분상한 | 40분 | 60분 |

전체 조건 방식은 두 번째40분을 온전히 줄 수 없어 추가 인정하지 않습니다. 부분 방식은 남은20분만 인정합니다. **어느 방식을 제품 기본으로 할지는 아직 결정하지 않았습니다.** 60분 상한은 임시 비교값이지 새 운영 상한이 아닙니다.

수행건시험에 별도 월2회 제한을 붙인 S35에서는 10월3회중2회,11월1회가 인정되어 360분이 나왔습니다. 수행건 판정을 월말 판정으로 바꾸지 않고 인정 제한만 월간으로 적용한 예입니다.

## 6. 실제 DB 관계에 저장됐는가

원본52개테이블을 PGlite에 생성하고, 규칙·측정·조건·효과·기간·한도·회차·부모revision·스티커·판정근거·인정·한도예약·권리·승인·원장·외부이행을 연결했습니다. 실행에서는 원본 FK·CHECK·UNIQUE·원장 불변 트리거를 사용했습니다. 단순히 계산 결과표만 작성한 것이 아닙니다. 52개 테이블 중 45개에 총 3,599개의 예시 행이 생성됐습니다. 사용·잔차·운영 권한처럼 이번에 사용하지 않은 테이블까지 실행 완료로 주장하지 않습니다.

- `condition-mapping.csv`: 원래조건→측정/비교/효과/한도 입력 관계.
- `output/Table-Counts.csv`: 각 시나리오·테이블의 실제 행 수. `output/relations.csv`는 행별 참조.
- `output/DB-state.json`: 가정DB의 행 사본.
- `output/ledger.csv`: 실제시험원장·귀속일·효력·상쇄관계.
- `output/results.json`: 최종실행값과 엔진검증.
- `output/independent-checks.json`: 별도최종값·중간상태검증.
