# 가족 규정·관계형 DB·표 UI·구조 변경 검토

## 범위와 참고자료를 선택한다

**문서 검토 / 독립 설계·시험 / 실제 운영 적용**을 구분한다. SQL·프로토타입·격상 검토 요청을 기존 규칙 초기화·자동 차감·서비스 교체·미래 예약·외부 알림 승인으로 해석하지 않는다. 파일·기기·커넥터의 현재 접근 가능성을 확인한다.

Play Routine이면 `references/play-routine-policy.md`와 최신 사용자 기본법·하위규정·시행령·승계 문서를 읽는다. 다른 서비스는 같은 방식으로 원문을 정리한다. 과거 경로·설치 버전·모델 검토를 현재 사실로 간주하지 않는다.

격상·격하·Supabase 가능 범위·후보 알림을 다루면 `references/hierarchy-change-review.md`를 읽고, 시험할 때 `references/verification-contract.md`를 읽는다. 실제 Grok 요청에는 `templates/grok-hierarchy-review-prompt.md`, 격리 재귀 조회 예시에는 `templates/school-hierarchy-example.sql`을 사용한다. 필요한 모듈만 읽는다.

웹·문서·SQL 제작은 해당 스킬을 따른다. 외부 사실 검색 전에 deep-research, 미래 자동화의 설계·구성에는 automation-and-scheduling, bulk LLM에는 builtin-llm-models 지침을 먼저 읽는다. 새 스킬 수정은 skill-creator 절차를 따른다.

## 1. 사실과 결정 경계를 추출한다

영구 번호·종류·목적과 일/주/월/사건 주기·업무 기간을 분리한다. Task/Quest/Lifestyle은 초기 규정 영역이지 영구 세 종류 제한이 아니다. 같은 교재의 일별 수행과 월간 성취를 서로 다른 인정 관계로 남긴다.

보상·명시 중립·무보상 미달·패널티 후보·부모 미확인·분류 잔차를 구별한다. 한 인정의 효과 1~2개, 독립 자산·단위, 인정 한도와 점검 횟수를 따로 추출한다. 두 번째 효과는 선택사항이다.

각 값을 원문·사용자 확정·예시 가정·미정으로 표시한다. 미정은 NULL/pending이며 0·없음·실패가 아니다. 이미 해결한 질문은 반복하지 않는다. 지급·차감·기간이 달라지는 충돌만 한 가지씩 확인한다. 재량형 생활 평가를 임의 세부 점수제로 바꾸지 않는다.

## 2. 규정 계보·승계·관할 변경을 설계한다

상위 목적 → 기본규정 → 하위 영역 → 처리규율 → 개별 시행규칙 → 월별 버전 채택을 정의한다. 규정·규칙·강화물 정체성 ID와 불변 버전을 분리한다. 개정·폐지·승계 사건에 효력 시각과 서버 기록 시각을 남긴다.

정확한 상위/하위/강화물/처리기 버전 조합을 채택한다. 다음 달은 복사본이 아니라 기존 승인 버전 참조다. 규칙 종료로 계정·가족·카탈로그·사건·권리·이행·원장을 삭제하지 않는다. 과거 원장 정정은 조정 행으로 남긴다.

School 격상·격하는 GOVERNS 관할 변경이다. REVISES·호환·자산 분류와 혼합하지 않는다. ID·집계 scope·열린 기간을 유지하고, 전후 측정·상한·배타·효과·처리기 계약을 비교한다. 미검토를 ‘보상 영향 없음’으로 표시하지 않는다. 단순 재귀 CYCLE 표시를 입력 차단·동시 승인 보장으로 설명하지 않는다.

승인 시각과 시행일을 분리하고 기존 사건은 당시 묶음을 참조하게 한다. 종류 ENUM/CHECK·관할 검사·UI/처리기가 신규 영역을 지원하는지 확인한다. 규정 개편만으로 보상 재발행·스티커 초기화·원장 정산을 호출하지 않는다.

## 3. DB 책임과 플랫폼 가능 범위를 분리한다

관계를 먼저 설명하고 요청된 경우 DDL을 작성한다. 최소 층은 가족·멤버십, 규정·규칙 버전, 조건·효과, 월별 채택, 자산·강화물, 회차·원사건·부모 확인, 스티커·기간, 한도 사용, 보상권·이행·원장, 잔차·민감 관찰이다.

가족별 복합 FK로 다른 가족의 자녀·규칙·강화물 연결을 차단한다. 읽기 권한과 부모 RPC 쓰기를 분리한다. 표 편집을 raw table UPDATE 권한으로 구현하지 않는다. 클라이언트가 지정한 부모 ID를 신뢰하지 않는다. SECURITY DEFINER 실행 권한·고정 search_path·현재 가족 역할을 검사한다.

스티커 아이콘은 표시 자원이다. 종류·원천 규칙·자녀·회차·확인 revision이 계산 정체성이다. 미확인/피드백 누락에서 0개·위반·차감을 추정하지 않는다. 약물·양육일기는 상태 조회·보상 규칙과 분리한다.

Supabase 공식 지원 / 현재 available / 실제 installed / 앱 연결·시험 완료를 구분한다. 읽기 전용 카탈로그와 공식 문서로 확인하고 미확인 층은 명시한다. PostgreSQL 정본과 외부 모델·알림·프런트를 구별한다. 긴 LLM·외부 호출을 DB 승인 트랜잭션 안에 넣지 않는다. 그래프 DB·AGE·큐·새 작업자를 필요 검증 없이 선행 조건으로 만들지 않는다.

## 4. 한도와 최고총액을 구현한다

한도 키는 가족·자녀·안정된 한도 범위·업무일/사건이다. 새 규칙 버전이나 월별 계획이 동일 기간 한도를 초기화하지 못하게 한다. 한 인정의 두 효과도 카운트는 한 번 소비한다. 초과 원사건은 보존한다. 동일 요청키에는 같은 결과, 같은 키 다른 내용에는 거절을 적용한다. UNIQUE·행/트랜잭션 잠금으로 보호한다.

최고구간 총액형과 누적 가산형을 별도 정책으로 둔다. 최고구간에는 다음을 사용한다.

```text
목표 권리총액 = 최고 충족 구간의 최종총액
추가권리 = max(0, 목표총액 - 기존 유효 순발행권리)
미이행액 = max(0, 유효 권리 - 실제 순이행)
```

미이행권리를 기존 권리에서 빼고 새권리를 발행하지 않는다. 하향 정정으로 발행/이행보다 목표가 작으면 검토 상태로 두고 자동 회수하지 않는다. 미확인 마감·실제 지급 시점을 점검한다. 월을 걸친 하나의 주간은 기간 정본 하나를 사용한다.

## 5. 부모 화면과 구조 제안을 단순화한다

상단 메뉴를 **운영표 / 규정 / 보상·원장 / 강화물 / 설정·기록**으로 나눈다. URL로 화면·기간·필터를 복원한다. 의미 있는 한 HTML 표 안에서 고정 머리글·식별열, 키보드 포커스·모바일 가로 스크롤을 제공한다.

부모 한 명 기준으로 선택 단계는 줄이되 DB를 단일 부모로 고정하지 않는다. 정상 PASS는 명시적 일괄 확인·선택 사유를 제공한다. 패널티·충돌·정정에는 근거를 요구한다. 감사·revision·요청키·소급은 시스템이 기록한다. 강화물은 태그로 재사용하고 계정·보호자·CSV는 기본 접힘/설정 메뉴로 옮긴다.

구조 점검은 규정 메뉴의 수동 버튼과 작은 카드부터 제안한다. 규칙 수·저빈도만으로 자동 격상/격하하지 않는다. 전후 관계·근거/반론·보상 검토 상태·‘검토/나중에/기각’을 보여주고 최종 변경 묶음과 시행일을 한 번 승인받는다.

프로토타입은 모의 데이터·별도 저장 키·초기화 범위를 표시한다. WebDev를 먼저 사용한다. 별도 초기화가 실제 실패하면 운영 폴더를 지우지 말고 독립 코드 패키지를 제공하며 생성·게시 완료를 꾸미지 않는다.

## 6. 알림·승인·적용 기록을 분리한다

제안 정본, 불변 사건, 승인 변경 묶음을 기존 수신자 알림과 연결한다. 해당 표·enum·RLS·read_at 권한·UI가 실제 있는지 확인한다. 특정 routine/보상권 로그를 제안 상태 정본으로 쓰지 않는다.

읽음≠승인≠실제 적용, 큐 처리≠외부 전달이다. 동일 기준의 기각 제안은 재알림하지 않는다. 변경된 근거는 후속 제안으로 연결하고 보류 재검토 조건은 부모 선택값으로 남긴다. Realtime은 갱신 신호, DB 알림은 재조회할 정본이다.

승인 RPC에서 활성 부모·family·검토 revision/입력 해시를 잠금 후 다시 확인한다. 바뀌었으면 재검토한다. 경쟁 구조 변경의 순환·복수 관할·효력 겹침을 원자적으로 차단한다. 자녀/상태 보호자에 제안 원문·승인 권한을 확대하지 않는다.

제안과 앱 알림 저장은 같은 짧은 트랜잭션, 외부 호출은 밖에 둔다. 외부 채널이 필요해질 때 outbox·시도 이력을 추가한다. 재전달·실패·중복 가능성을 기록하고 외부 정확히 한 번 전달을 약속하지 않는다. 감사 증거와 개인정보 보존/삭제를 함께 설계한다.

## 7. 독립 실행·실제 Grok 검토를 수행한다

`references/verification-contract.md`의 해당 반례를 독립 기대값·중간 상태로 시험한다. SQL 파싱에 그치지 말고 격리 PostgreSQL에서 함수·FK·제약을 실행한다. PGlite 순차 검증을 실제 다중 연결·Supabase RLS·운영 지급 시험이라고 표시하지 않는다.

사용자가 Grok를 요청하면 실제 응답을 받거나 사용 불가를 명시한다. 현재 모델·공식 계약·저장된 인증을 확인하고 구조와 익명화 근거만 보낸다. 실제 응답 모델·입력 파일 해시·완결·시각·원문을 보존한다. 미완결 응답을 승인 가능한 검토로 쓰지 않는다. AI 의견을 사용자 승인으로 간주하지 않는다.

원문과 Manus의 채택/보정/보류/기각을 분리한다. 기존 검토의 당시 대상과 새 설계 차이를 밝히고 후속 수정본을 재검증한 것처럼 설명하지 않는다. 메뉴·모바일·권한·후보 중복·신호 유실·승인 경쟁·최고총액 반례를 해당 실행 환경에서 시험한다.

산술만 확인할 때 `scripts/check_policy_math.py --self-test` 또는 명시적 입력 JSON을 사용한다. 이 도구는 DB·동시성·지급 검증이 아니다.

## 출력·완료 기준

요청 범위에 맞는 관계·확정/미정표·엔티티 사전·시행규칙 매핑, 요청된 SQL/seed/샘플·검증 결과와 프로토타입 소스를 같은 계약으로 맞춘다. 구조 검토에는 Supabase 범위·보상 영향·알림 카드·승인/적용 기록·실제 모델 원문과 반영 사항을 포함한다.

운영 미적용·미구현·미수행 시험을 해당 내용 옆에 밝힌다. 정적 문서 QA는 실제 Grok 호출·DB 실행·운영 검증의 대체 증거가 아니다. 파일을 확인해 절대 경로 링크로 전달하고 초보 사용자의 다음 행동은 한 단계만 제시한다. 요청하지 않은 GitHub 게시·배포·예약·초기화를 추가하지 않는다.
