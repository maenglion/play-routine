# 규정 격상·격하 검토와 알림·승인 이력

## 사용 범위를 먼저 구분한다

규정의 독립/통합, School 같은 신규 영역, Supabase 처리 가능성, 보상 영향, AI 후보 알림을 검토할 때 이 절차를 사용한다. 검토·SQL 샘플 요청을 운영 migration·미래 예약·알림 발송·자동 승인 권한으로 확대하지 않는다. 실제 운영 자료, 미배포 설계, 격리 시험을 각각 표시한다.

## 1. 정체성과 관계를 점검한다

규정 정체성 ID, 원문 버전, 관할 GOVERNS, 개정 REVISES, 호환/참조 관계를 분리한다. 재귀 조회는 승인된 GOVERNS만 따라가고 버전과 관계 양쪽의 효력 구간을 필터링한다. [시작, 종료) 경계를 사용해 시행일에 옛 관계와 새 관계가 동시에 활성화되지 않게 한다.

Task 아래 School을 기본법 직속으로 이동해도 같은 목적의 규정 ID와 해당 규칙 ID를 유지한다. 격상은 새 도메인 분리, 격하는 도메인 통합이다. 삭제·폐지·보상 감소를 격하로 취급하지 않는다. 구조 번호 변경은 표시 문제이며 계산 정체성을 재발급할 이유가 아니다.

ENUM/CHECK, 관할 종류 일치 함수, 부모/자녀 UI 필터, 실제 처리기의 종류 분기를 함께 읽는다. SCHOOL 허용 여부를 샘플 text 컬럼만 보고 운영 지원이라고 판단하지 않는다. 측정·처리 계약은 도메인 이름과 위계 깊이가 아니라 승인된 정의를 참조하게 한다.

`templates/school-hierarchy-example.sql`은 TEMP 자료와 ROLLBACK을 사용하는 조회 예시다. PG14+ 지원 여부를 확인하고 격리 엔진에서 실행한다. 이는 RLS·입력 순환 차단·동시 승인·운영 DDL이 아니다. CYCLE이 순환 행을 표시하는 것과 잘못된 변경을 거절하는 것은 다르다. 같은 관계 쌍의 재시행 이력을 UNIQUE가 막는지도 확인한다.

## 2. 보상 의미 보존을 확인한다

위계 관계와 자산 분류를 같은 트리로 만들지 않는다. 규정의 격상만으로 자산·금액·스티커·원장을 재분류하지 않는다. 버전·승인·이력이라는 관리 패턴은 강화물 정의에도 재사용하되 별도 내용 검증을 둔다.

변경 전후 다음 계약을 비교한다: 측정 방식, 효과 자산/정의 버전/수량, 인정 횟수, 한도와 적용 범위, 기간 경계, 배타 조건, 집계 scope, 현재 열린 기간의 관할 묶음, 기발행 권리·실제 이행·과거 원장.

상위 상한·배타 조건이 새 부모에 연결되지 않으면 액수가 같아도 의미가 달라진다. ‘관할만 변경 / 계산 개정 필요 / 기간·권리 재검토 필요 / 미검토’로 판정한다. 미검토를 영향 없음으로 바꾸지 않는다. 계약을 유지할 수 없으면 별도 정책 개정·전환 승인 전 게시를 막는다.

학교 예시: 유효 권리10,000원 + 실제 이행10,000원 + 목표15,000원 → 추가권리5,000원이다. School 독립을 이유로 새 scope/새 기간을 만들어15,000원을 다시 발행하지 않는다. 열린 기간은 당시 묶음을 유지하며 새 기간부터 적용하는 것은 기본 제안일 뿐, 실제 시행일·주간 경계는 부모 승인값이다.

## 3. Supabase 가능 범위를 증거로 확인한다

현재 프로젝트와 키는 지정된 health 방식으로 확인한다. 구조 확인이 필요하면 승인 범위에서 읽기 전용으로 `pg_available_extensions`와 `pg_extension`, 테이블·함수·권한을 읽는다. 제공자 공식 기능, 현재 available, 실제 installed, 앱 연결·운영 시험 완료를 구별한다. Publishable Data REST 접근이 migration 권한이나 시스템 카탈로그 접근을 보장하지 않는다. 접근 불가이면 그 층을 미확인으로 표시한다.

규정 관계·재귀 SQL·가족 권한·승인 RPC·제안/보상/원장 정본은 PostgreSQL 중심으로 설계한다. Grok 추론·프런트 화면·외부 이메일/메신저 전달은 별도 연동이다. 플랫폼 지원만으로 예약 작업·큐·Manus 분석 작업자가 이미 생겼다고 설명하지 않는다.

Edge Functions 실행/idle/라이브러리 제한과 요청할 모델의 실제 시간을 최신 공식 문서로 확인한다. 긴 LLM·메일 호출을 부모 승인 요청이나 DB 트랜잭션 안에 넣지 않는다. 짧은 트랜잭션은 작업을 기록하고 외부 처리는 별도 실행한다. 과거 ‘PG17.11, cron/net/mq available·미설치’는 당시 프로젝트 관찰일 뿐 새 작업의 현재 사실이 아니다.

PostgreSQL 재귀·관계 모델로 충분하면 그래프 DB/AGE를 선행 조건으로 두지 않는다. AGE의 공식 존재가 해당 Supabase 프로젝트의 설치 지원을 뜻하지 않는다. 실제 필요와 제공자 지원을 별도 확인한다.

## 4. 실제 독립 모델 검토를 수행한다

사용자가 Grok를 요청하면 실제 모델 응답을 받거나 사용 불가를 명시한다. 저장된 인증·현재 모델 목록·공식 요청 계약을 확인한다. `templates/grok-hierarchy-review-prompt.md`에 최신 자료와 확정/미정표를 넣는다. 외부 전송은 구조·익명화 근거만 사용하고 아동 행동 원문·복약·가족 식별자·인증값은 제외한다.

각 입력의 파일명/버전/SHA-256, 실제 요청·응답 모델, 요청/완료 시각과 완결 여부를 보존한다. 스트리밍은 종료 표시·finish reason·본문을 확인한다. 실패/미완결/잘림을 최종 검토로 쓰지 않는다. 인증 오류를 인증값과 함께 출력하지 않는다. bulk 호출이면 builtin-llm-models 지침을 먼저 읽는다.

원문은 그대로 보존하고 ‘채택 / 보정 / 보류 / 기각’으로 Manus 반영 결과를 분리한다. 모델이 설계 표를 ‘운영’이라고 부르거나 새 정책을 제안하면 실제 근거로 수정한다. 1차안을 검토한 결과를 후속 수정본의 재검증이라고 표시하지 않는다. 코드 실행이나 동시성 시험을 하지 않은 모델 답변은 그런 시험의 증거가 아니다.

## 5. 후보 알림과 실제 변경 승인을 분리한다

현재 부모 한 명 운영은 규정 메뉴의 수동 ‘구조 점검’과 낮은 우선순위 카드부터 제안한다. 항목 수·저빈도만으로 격상/격하를 자동 결정하지 않는다. 명확한 독립 목적·평가 범위·반복 예외·중복 정의와 반례를 근거로 제안한다.

카드에는 전후 관계, 대상 범위, 제안 이유·반론, 보상 영향 검토 상태와 ‘검토/나중에/기각’을 표시한다. 부모 체크 화면을 가리지 않는다. 승인 화면에서 정확한 변경 묶음·기준 revision·시행일을 한 번 명시한다.

알림 읽음≠승인, 부모 승인≠실제 적용, 큐 처리≠외부 수신≠읽음이다. 기각된 같은 대상/같은 입력 해시/같은 제안 유형은 재알림하지 않는다. 중요한 버전·근거 변경은 이전 제안의 후속으로 기록한다. 보류 재검토 시점/조건은 부모가 선택한 값만 남긴다.

앱 알림을 DB에 남기고 재접속/신호 유실 시 재조회한다. Realtime은 갱신 신호다. 기존 알림표·enum·수신자 RLS·read_at 권한과 실제 UI를 확인한 뒤 재사용한다. 자녀/상태 전용 보호자에게 제안 원문·승인 권한을 확대하지 않는다. 현재 유효한 부모 역할과 수신자 조건을 모두 적용한다.

외부 알림은 사용자가 경로를 선택한 뒤 붙인다. 인증된 앱 링크와 최소 내용만 보내고 아이 행동·약물 상세는 제외한다. 검토 요청만으로 cron/trigger/메일 발송을 설정하지 않는다. 미래·상시 자동화를 실제 구성할 때 automation-and-scheduling 및 관련 스킬을 읽고 적절한 실행 환경을 사용한다.

## 6. 최소 정본과 동시 승인 보호를 설계한다

제안 정본 `governance_proposals`, 불변 사건 `governance_proposal_events`, 승인 묶음 `governance_change_sets`를 기본으로 기존 수신자 알림과 연결한다. 명칭은 제안이며 현 DB에 있다고 가정하지 않는다. routine 요청/보상권 이력에 새 제안 상태를 억지로 넣지 않는다. 검토 원문이 크면 접근 제한된 별도 참조를 둔다.

사건에는 실제 행위자·유형·서버 시각·이전/이후 상태·사유·요청키·기준 버전을 남긴다. 모델 검토에는 입력 해시·모델·완결·반론을 연결한다. 승인 묶음에는 승인자/approved_at와 시행일·적용 범위·결과를 분리한다. 예약/적용/실패 이력은 append-only로 남기고 원문을 덮어쓰지 않는다.

승인 RPC는 활성 부모의 family 권한, expected revision·입력 해시·최신 버전을 잠금 후 확인한다. 변경됐으면 재검토한다. 같은 요청키에는 기존 결과, 같은 키 다른 내용에는 거절을 적용한다. 순환·동시 복수 관할·효력 겹침·상위 상한/호환 연결을 원자적으로 검사한다. 경쟁하는 가족 내 구조 변경은 공통 잠금이나 동등한 직렬화로 보호한다. 임의 클라이언트 부모 ID·test_mode 우회를 신뢰하지 않는다.

제안과 앱 알림 기록은 같은 짧은 트랜잭션, 외부 처리와 전송은 트랜잭션 밖에 둔다. 외부 채널이 필요해질 때 outbox와 시도 사건을 추가한다. 큐 재전달·중복 전송·장기 실패를 가정하고 제공자 멱등을 활용하되 외부 정확히 한 번 전달을 약속하지 않는다. 감사 불변성과 개인정보의 보존·삭제 정책을 함께 설계한다.

## 출력 계약

1. 결론과 현재 구현/설계/미확인 경계.
2. 변경 전후 위계와 유지할 영구 ID·기간·계산 계약.
3. Supabase 가능/별도 연동/현재 미설정 구분과 확인 근거.
4. 보상 영향·반례·게시를 막을 조건.
5. 부모 알림 한 카드와 승인/적용 흐름.
6. 최소 정본·권한·멱등·동시성·실패 복구.
7. 실제 Grok 원문·입력 해시·반영 결과·미수행 시험.

규정 검토와 보상 계산/알림 발송/운영 배포를 구분해 완료를 보고한다. 요청하지 않은 배포·초기화·자동화를 추가하지 않는다.
