# 독립 검증 계약

## 최소 반례

1. 생활 +15분 × 4사건 / 하루 한도3 → 4원사건·3인정·45분.
2. 같은 request key 재전송 → 사건·한도소비·권리 추가 없음. 같은 키 다른 payload → 거절.
3. 한 인정의 시간+돈 두 효과 → 한도 소비는 한 번, 자산 권리는 둘.
4. 같은 규칙을 새 버전/새 월 계획으로 다시 연결해도 동일 업무일 한도 초기화 금지.
5. 타 가족 자녀·버전·기간·강화물 FK/부모 API 연결 → 거절.
6. 자녀·조회 보호자·멤버십 없음 → 부모 확인·권리 발행·민감 기록 접근 거절.
7. 학교 확정 4/5/7/8개 → 0/10,000/10,000/15,000원.
8. 교사 피드백 미수신·기본 미확인·미정 동시 조건 → 최종 마감 보류.
9. 5개권리10,000 → 8개권리추가5,000. 미이행10,000을 이유로15,000 새권리 발행 금지.
10. 같은 권리 지급10,000 뒤 목표15,000 → 추가권리5,000, 추가이행은 현재 미이행액.
11. 월을 걸친 하나의 주간 → 월계획이 둘이어도 기간 정본과 최종총액 하나.
12. 지급 후 판정 하향 → 검토 상태. 자동 회수·과거 원장 삭제 금지.
13. 수행일·입력일·확인일·효력일이 다른 소급 → 원행 보존, 정정 이벤트/원장 조정 별도.
14. 같은 사건 일반/특수 패널티 겹침·규칙 미분류 → 임의 선택 없이 보류.
15. 표형 UI 정상 PASS 일괄 확인은 부모의 명시적 행위. 모호·미확인·패널티를 일괄 차감하지 않는다.

## 기술 시험 범위

SQL 파싱 성공, 실제 격리 PostgreSQL 실행, REST 권한 시험, 운영 DB 적용, 실제 이메일, 병렬 부하 시험은 서로 다른 검증 단계다. 실행하지 않은 단계를 통과했다고 쓰지 않는다.

PGlite는 함수·FK·제약의 순차 실행 검증에 유용하다. 단일 연결을 사용한 결과를 실제 다중 연결 동시성·Supabase RLS·서비스 역할 우회 방지 시험으로 표시하지 않는다. 테스트에 JWT claims를 직접 설정하는 것은 격리 fixture의 관리 동작이다. 실제 클라이언트가 claims를 지정할 수 있도록 구현하지 않는다.

SQL SECURITY DEFINER 함수는 최소 권한·고정 search_path·명시적 가족 멤버십·검증된 호출자를 사용한다. 부모 ID를 클라이언트 인자로 받아 신뢰하지 않는다. 서로 다른 행을 보는 CHECK로 집계 한도를 보장하려 하지 말고 UNIQUE/FK/잠금/RPC로 책임을 분리한다.

## 검토 원문 보존

Grok 등 2차 검토에는 현재 문서·DDL의 정확한 해시/버전과 확정·미정 표를 전달한다. 모델 ID·완결 상태·대상 문서를 기록한다. 실제 응답 없이 ‘그록 검증 완료’라 쓰지 않는다. 검토자가 제안한 새 정책은 사용자 승인 전 확정값으로 바꾸지 않는다.

## 격상·격하와 알림 추가 반례

1. School 독립 전후 regulation_id/rule_id/학교 집계 scope가 동일하고 과거 조회는 옛 관할을 반환한다.
2. 같은 열린 주간에 격상·격하 후에도 기존 권리10,000원이 유지된다. 목표15,000원에는 추가5,000원만 발행한다.
3. 격상만 했지만 상위 상한·배타 연결이 사라짐 → 영향 없음이 아닌 게시 차단/계산 개정 필요.
4. 승인 시각보다 미래인 시행일 전후와 정확한 경계 → 동일 시점 복수 부모·옛/새 버전 동시 효력 없음.
5. 같은 관계 쌍의 종료 후 재시행 → 원문 이력 보존하며 표의 UNIQUE 때문에 정상 이력이 막히는지 확인한다.
6. 두 세션이 서로 다른 가지를 동시에 이동해 순환을 만들려 함 → 실제 다중 연결에서 한 변경 이상 거절. 순차 CYCLE 조회만으로 이 시험 통과라고 하지 않는다.
7. 부모 검토 뒤 기준 규정/제안 revision 변경 → 승인 거절·재검토. 서버가 최신안으로 자동 재승인하지 않는다.
8. 승인 요청키 재전송 → 같은 변경 묶음. 같은 키 다른 내용 → 거절.
9. 알림 read_at만 변경 → 제안은 미승인. 승인됐으나 적용 실패 → 승인/실패 이력 분리, 적용 완료로 표시 금지.
10. 기각된 동일 입력 해시·대상·유형 → 반복 알림 없음. 중요한 기준 변경은 후속 제안으로 연결한다.
11. 자녀·상태전용 보호자·타 가족·부모 연결 해제 → 제안 원문/승인 RPC 접근 거절. UI 숨김만으로 통과라고 하지 않는다.
12. Realtime 신호 유실·로그아웃 → 앱 재접속 시 DB 알림 정본을 재조회한다.
13. 큐 재전달·외부 전송 성공 후 기록 전에 작업자 종료 → 앱 알림 중복 차단, 제공자 멱등/재시도·중복 가능성 명시. 정확히 한 번 외부 전달 보장 금지.
14. Grok 인증 실패·미완결·잘린 응답 → 검토 완료/승인 가능으로 표시 금지. 기존 운영은 유지한다.
15. 격상으로 도메인명 변경 → PASS가 퍼센트제로 바뀌거나 인정 한도·자산 단위가 바뀌지 않는다.

## 재사용 스킬 확인 사례

- “School을 Task와 동등하게 올리고 재귀 SQL 보여줘” → 최신 관계·효력·종류 제약을 읽고 TEMP/ROLLBACK 조회 예시를 제공한다. 운영 승인·보상 재발행은 하지 않는다.
- “Supabase로 전부 처리하고 필요하면 알려줘” → 플랫폼 가능/현재 설치/외부 모델·알림을 구분하고 카드·승인 이력만 설계한다. 이 말만으로 예약·트리거·LINE 발송을 만들지 않는다.
- “그록에게 검토해줘” → 익명화된 현재 입력과 해시로 실제 모델 응답을 받고 완결·대상·반영 범위를 밝힌다. 과거 검토나 AI 관점 모사를 실제 새 검토라고 쓰지 않는다.
