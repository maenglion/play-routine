# 실제 Grok 검토 요청 템플릿

다음은 익명화된 규정 서비스의 구조 검토이다. 코드를 실행하거나 정책을 승인한 것으로 답하지 말고, 문서에 없는 기능을 운영 구현이라고 가정하지 말라. 사용자의 확정 금액·한도·주기와 미정 사항을 구분하라.

## 검토 입력을 채운다

- 목적과 요청 범위: <격상/격하/관할 이동, 설계/시험/운영 중 어디까지인지>
- 전후 관계: <기본법 → Task → School에서 기본법 → School 등>
- 자료: <현재 원문·DDL·조회/승인 함수·익명화 UI, 정확한 버전/해시>
- 현재 환경 확인: <프로젝트 관찰 날짜, PostgreSQL 버전, 확장 available/installed, 실제 알림표/UI 유무, 미확인>
- 계산 보존 계약: <영구 rule_id, 집계 scope, 열린 기간, 측정·상한·배타·효과 버전, 기존 권리/이행/원장>
- 확정/미정표: <사용자 확정값과 설명용 가정>
- 1차안: <부모 카드, 승인 묶음, 사건 이력, 권한, 멱등·실패 처리>

외부 전송 전에 실제 가족 ID·아이 이름·이메일·복약/행동 상세·키/토큰/연결 비밀번호를 제거하라. 필요한 구조 사례만 사용하라.

## 요청한다

한국어로 결론, Supabase 정본 가능 범위와 별도 연동/미설정 기능, 보상 영향의 실제 반례, 부모 알림 카드, 기록·동시 승인 보호, 지금 보류할 복잡성을 검토하라. 6개 이내의 필수 보완을 제시하되 자료의 테이블·필드와 연결하라.

새 집계 scope를 만들 때 이중 발행되는지, 같은 권리의 실제 이행액을 발행식에서 다시 빼는지, 상위 상한 상속이 끊기는지 검토하라. 종류 ENUM/CHECK·관할 검사·UI/처리기 분기와 CYCLE 진단이 운영 입력 차단을 대신하는지 구분하라.

검토한 버전 이후의 변경·운영 부하·RLS·실제 알림 전달을 검증했다고 주장하지 말라. AI 권고를 사용자 승인으로 취급하지 말라. 없는 근거는 미확인으로 표시하라. 읽음/승인/실제 적용, 큐 처리/외부 전달을 분리하고 부모 단일 운영에 불필요한 단계를 늘리지 말라.

## 응답 뒤 별도로 보존한다

실제 모델 ID, 입력 파일별 SHA-256, 요청·완료 시각, finish reason/스트림 종료와 본문, 원문, Manus의 채택/보정/보류/기각을 연결한다. 완결되지 않은 응답은 최종 검토로 사용하지 않는다.
