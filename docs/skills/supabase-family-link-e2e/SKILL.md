# 실제 이메일 부모·자녀 연결 종단시험

## 원칙

단위시험, API 발송 수락, 실제 받은편지함 수신, 인증, 가족 연결을 별도 결과로 기록한다. 하나를 다른 단계의 성공으로 대체하지 않는다. 실제 수신·수락을 확인하기 전 E2E PASS를 선언하지 않는다.

사용자에게 한 번에 한 행동만 요청한다. 비밀번호·전체 인증 URL·access token·refresh token을 채팅이나 작업기록으로 받지 않는다. 메일 확인과 비밀번호 입력은 계정 소유자 브라우저에서 수행하게 한다. 이미 제공된 비밀값을 반복하지 않는다.

이 절차는 실제 문제 진단에서 추출했다. 절차 패키지 검증과 해당 앱의 종단시험 완료는 별개다. 기존 가족·계정·원장을 임의 이관·삭제하지 않는다. 프로젝트 전환·데이터 삭제·계정 보안 변경에는 범위와 권한을 확인한다.

## 1. 대상과 연결 확인

1. 현재 실행환경, 코드 경로, 공개 앱 URL, Auth와 DB 프로젝트를 확인한다. 복구 후 경로·브라우저 로그인·환경변수가 그대로라고 가정하지 않는다.
2. 현재 연동 설정과 환경 문서를 확인한다. 비밀값은 출력하거나 소스에 넣지 않는다. 별도 REST 연동이 다른 프로젝트일 수 있다.
3. WORKLOG, migration, Auth router, UI를 읽어 실제 테이블·컬럼·RPC를 확인한다. 예시 schema를 운영 schema로 추정하지 않는다.
4. Auth GET /auth/v1/health를 apikey 헤더로 확인한다. REST OpenAPI 루트 실패를 Auth 장애로 해석하지 않는다.
5. PostgreSQL 연결을 별도로 확인한다. 비밀 포함 연결 문자열·오류 원문은 출력하지 않는다.
6. DNS ENOTFOUND 또는 pooler tenant/user not found이면 프로젝트 상태와 최신 연결정보를 확인한다. 일시중지·삭제·이동·대상 오입력 중 어느 것인지 확정하기 전 다른 DB로 바꾸지 않는다.

## 2. 메일 종류와 callback 확인

1. Auth Site URL과 허용 Redirect URL을 공개 앱 기준으로 확인한다. 프로덕션에 localhost를 남기지 않는다.
2. 링크 요청이 명시적으로 public origin을 전달하고 서버는 허용 origin만 수용하는지 확인한다.
3. 실제 템플릿을 확인한다. 링크-only면 확인 링크 → 앱 복귀 → 비밀번호 설정 UI를 사용한다. 숫자 OTP UI를 남기고 링크를 코드로 설명하지 않는다.
4. 링크를 계정 소유자의 브라우저에서 열게 한다. 부모 브라우저에서 자녀 링크를 열면 세션이 바뀔 수 있다.
5. 앱 복귀 후 세션 복원과 비밀번호 설정 조건을 확인한다.

브라우저 implicit 방식은 루트 `/`도 유효한 수신 지점이다. Next.js PKCE·서버 cookie callback과 혼합하지 않는다. 관리 화면에 접근하지 못하면 무효 토큰의 `/auth/v1/verify` GET을 redirect 자동 추적 없이 요청해 실효 Site URL·공개 루트·전용 callback·외부 fallback 정책을 확인할 수 있다. 실제 사용자 토큰·메일 발송은 사용하지 않는다. 이 정책시험은 정상 이메일 성공시험을 대신하지 않는다. 오류 fragment·인증정보를 안전하게 정리하고 만료 안내·비밀번호 설정 화면 우선순위도 확인한다.

## 3. 구현 검증

다음을 단위시험과 코드에서 확인한다.

- 부모 Auth 검증 → 활성 부모 membership → 같은 가족·초대·이메일 fingerprint → 활성·미만료·미수락 조건.
- 자녀의 인증 이메일과 초대 이메일 일치. trim/lowercase 외 provider-specific 점·plus 주소 추정 금지.
- 재전송은 새 초대나 프로필을 생성하지 않음.
- 자녀 첫 연결과 부모 재전송은 같은 빈도 제한 사용. DB 요청 예약과 제한 확인의 동시성 검증.
- 권한 없음·초대 없음·이메일 불일치는 일반 응답으로 존재 여부 누출 방지. 일반 응답은 발송 성공 확인이 아님.
- REQUESTED, SENT, FAILED, RATE_LIMITED 감사 구분. SENT는 제공자의 요청 수락이지 수신 보증이 아님.
- 오류 코드·상태·요청 상관관계만 저장. 이메일·토큰·비밀 포함 원문 저장 금지.
- 단위시험과 실제 연결시험을 분리하고 제외·실패를 보고.

Play Routine 적용정보가 필요하면 `references/play-routine.md`를 읽는다.

## 4. 사용자 협업 종단시험

각 단계 완료 후 다음 한 단계만 요청한다.

1. 부모가 실제 이메일로 가입·확인하고 링크가 공개 앱으로 돌아오는지 확인한다.
2. 부모가 브라우저에서 비밀번호 설정 후 가족을 만든다.
3. 자녀 이름과 실제 이메일로 초대를 한 번 만든다. ACTIVE 초대가 있으면 재전송으로 진행한다.
4. 초대 생성이 DB 저장만 하는 구조면 부모 재전송 또는 자녀 첫 연결 버튼으로 발송 API를 실제 호출한다.
5. 요청 시각과 DB 감사 REQUESTED → SENT/FAILED 또는 RATE_LIMITED를 대조한다.
6. 자녀가 받은편지함·스팸함에서 최신 메일을 확인하고 자기 브라우저로 링크를 연다. URL 대신 도착 여부와 화면 결과만 공유하게 한다.
7. 자녀가 비밀번호를 설정하고 정확한 가족 초대를 수락한다.
8. DB에서 초대 ACCEPTED, profile ACTIVE, CHILD membership·principal 연결을 확인한다.
9. 부모가 비밀번호로 재로그인해 연결된 자녀를 확인한다.
10. 다른 가족 접근과 CSV 차단을 실제 RLS 또는 권한 시험으로 확인한다. mock 경로 시험을 실RLS 검증이라고 하지 않는다.

수락 완료 보고 후 실제 DB를 읽기 전용으로 대조한다. ACCEPTED 초대의 accepted principal과 ACTIVE profile principal, 인증 이메일 fingerprint가 같고 ACTIVE CHILD membership이 정확히 1건인지 확인한다. 링크 감사와 부모 알림은 최초 수락 1회인지 확인한다. 이메일 확인·비밀번호 설정·로그인시각의 유무는 boolean으로 출력하고 이메일·토큰·계정 ID는 불필요하게 노출하지 않는다. 가족별 RLS는 실제 역할로 읽기 트랜잭션에서 검증한 뒤 롤백한다. 재로그인·부모 화면 확인은 사용자 보고나 브라우저 증거가 없으면 별도 대기로 남긴다.

## 5. 미수신 진단

| 관측 | 우선 판단 | 다음 행동 |
|---|---|---|
| 감사 0, 자녀 Auth 생성 0 | UI 미진입 또는 서버 요청 미도달 | 기본 모드·버튼·API 호출·요청 오류 확인 |
| RATE_LIMITED | 앱 제한 | 간격·한도 확인, 재시도 남발 금지 |
| REQUESTED + FAILED | Auth 요청 오류 | 코드·상태로 callback·제공자 제한·SMTP 확인 |
| REQUESTED + SENT, 실제 미수신 | 수락 후 전달 문제 가능 | 스팸·주소·메일 정책·SMTP 로그 확인 |
| 메일 도착, localhost 복귀 | callback 오류 | Site URL·Redirect URL·요청 origin 동시 수정 |
| 인증 후 초대 없음 | 이메일 불일치·만료·취소·기수락 가능 | fingerprint·상태·principal·가족 대조 |
| ACTIVE_INVITATION_EXISTS | 유효 초대 중복 생성 | 기존 초대 재사용, 새 profile 생성 금지 |
| Auth DNS/DB 연결 실패 | 대상 서비스 불가 | 프로젝트 상태·연결정보 확인 후 재개 |

기본 SMTP가 임의 수신자를 제한하는지 제공자의 현재 공식 문서와 실제 오류로 확인한다. 일반 안내만 보고 성공으로 판단하지 않는다.

## 6. 데이터 정리

삭제 요청이 없으면 유지한다. 요청이 있으면 정확한 대상을 조회하고 필요한 확인을 받는다. 연결 전 테스트만 정리하려면 ACTIVE + 미수락 + PENDING_LINK + principal 없음 조건을 확인한다. 실제 외래키·이벤트·수락 기록을 검토해 하나의 트랜잭션으로 정리한다.

부모 사용자·가족·활성 membership·연결 자녀·원장은 보존한다. 전후 건수·영향을 기록한다. 복구 후 현재 조회가 불가하면 이전 삭제는 ‘이전 실행 기록’이라고 쓰고 재실행하지 않는다.

## 7. 인계·완료 기준

WORKLOG에 일자별 결정, 코드 변경, migration 적용 여부, 데이터 영향, 명령과 결과, 배포 여부, 실패·다음 한 단계를 추가한다. 결정일을 확인할 수 없으면 근거 버전 날짜 또는 날짜 미상으로 기록한다.

- [ ] Auth·DB 실제 연결
- [ ] 실제 부모 가입·메일 복귀·비밀번호 설정
- [ ] 실제 자녀 수신·공개 앱 복귀
- [ ] 수락과 ACTIVE DB 연결
- [ ] 부모 재로그인·자녀 표시
- [ ] 타 가족 RLS·무권한 발송/CSV 차단
- [ ] 재전송·제한·중복 초대 회귀
- [ ] 작업기록·소스·배포 인계

한 항목이라도 남으면 부분 완료와 정확한 차단 조건을 보고한다.
