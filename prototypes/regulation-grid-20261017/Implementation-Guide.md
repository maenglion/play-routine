# Play Routine — 규정형 DB와 표 중심 부모 화면

**부모 화면은 한 명이 쓰는 운영표로 단순화하고, DB는 가족·자녀·규정 버전·원사건·보상권을 분리하는 구조로 유지한다.** 이번 파일은 10월 시행령과 세 하위규정에 맞춘 독립 설계·SQL·모의 웹 코드다. 기존 운영 DB, 부모·자녀 연결, 기존 규칙, 실제 원장을 초기화하거나 교체하지 않았다.

## 1. 어떤 정본을 연결하는가

기준은 기본법·3대 하위규정 v0.6, 법령형 구조·월별 승계 v0.2, 10월 시행령 v0.5다. 원문은 `source-documents/`에 함께 보존했다. 운영 규정의 최종 승인 버전 ID가 발급된 것은 아니므로 샘플 계획·관계가 존재한다고 실제 게시된 것으로 해석하지 않는다.

```text
기본규정 ID@버전
  ├─ Task 하위규정@버전 ───── T-001~007
  ├─ Quest 하위규정@버전 ──── Q-001~003
  └─ Lifestyle 하위규정@버전 ─ L-001~016
               ↓ 정확한 버전 조합과 공통 처리규율
         10월 계획의 버전 채택 목록
               ↓
       예정회차 / 실제 발생 사실
               ↓ 부모 확인·정정
     인정한도 사용 / 학교 종류별 스티커
               ↓
       안정된 업무기간 / 보상권
               ↓ 실제 제공·이행
       향후 정산 원장과 조정행
```

11월 계획은 규칙을 복사하지 않고 계속 유효한 같은 ID·버전을 채택한다. 새 강화물 정의나 상위 규정이 개정되면 영향받는 하위 버전 조합을 재검토한다. 법령 개정과 특정 자녀의 과거 수행 사실은 다른 기록이다.

## 2. 관계를 나누는 기준

| 관계 층 | 이 설계에서의 역할 | 분리해야 하는 이유 |
|---|---|---|
| 가족·자녀·멤버십 | 해당 가족의 부모만 인정·권리 처리를 호출 | 화면을 한 부모 기준으로 만들어도 다른 가족 접근을 허용하지 않음 |
| 규정 ID·불변 버전 | 기본·Task·Quest·Lifestyle·공통 처리규율의 계보 | 번호 유지와 내용 개정을 동시에 보존 |
| 시행규칙·조건·효과 | T/Q/L 번호, 조건별 1~2개 독립 효과 | 달성 한 번에서 보상 둘을 만들되 인정 횟수를 두 번 소비하지 않음 |
| 월별 계획·채택 | 정확한 규칙·상위규정 버전 참조 | 월마다 재등록·복사·한도 초기화하지 않음 |
| 자산·강화물 정의 | 미디어 분, 현금 원, 쿠페이머니 원, 소원 내용 | 서로 다른 단위를 자동 합산·환산하지 않음 |
| 회차·원사건·확인 | 실제 수행, 입력, 부모 판단과 근거 | 아이 신고나 기록 공란을 부모 확정으로 바꾸지 않음 |
| 스티커 종류·기간 | 학교 기본과 칭찬의 원천 구별, 해당 학교 기간 합산 | 아이콘이 같아도 다른 규칙·기간 스티커를 섞지 않음 |
| 인정 버킷·사용 | 자녀·안정 규칙 범위·업무일의 한도 소비 | 규칙 버전이나 월 계획 변경이 같은 날의 한도를 리셋하지 않음 |
| 권리·정정·이행 | 받을 권리와 실제 받은 금액·쿠폰을 구별 | 미지급 권리 재발행이나 권리+지급의 이중 공제 방지 |
| 민감 복약 기록 | 아침·저녁 관찰을 별도 저장 | 약물 기록 누락에서 패널티를 만들지 않음 |

정확한 테이블·키·강제 제약·미구현 범위는 [엔티티 관계표](database/entity-map.md)에 있다. [DDL](database/schema.sql)과 [26개 규칙 시드](database/seed.sql)는 `pr_design`이라는 **격리 스키마**의 설계용이다. 운영 Supabase migration 파일이 아니다.

## 3. 생활습관의 하루 인정 한도

L-001은 부모가 인정한 실제 수행 한 건당 +15분, 하루 최대 3회다. 수행 원사건 4건을 삭제하거나 3건으로 줄이는 방식이 아니다.

| 원사건 | 부모의 인정 요청 | 한도 사용 | 예정 효과 |
|---|---|---:|---:|
| 1회차 | 실제 수행 확인 | 1 | +15분 |
| 2회차 | 실제 수행 확인 | 1 | +15분 |
| 3회차 | 실제 수행 확인 | 1 | +15분 |
| 4회차 | 실제 수행 확인 | 0 · 초과 | 0분 · 원사건 유지 |
| 합계 | 원사건 4건 | 3 | **45분** |

한도 버킷의 식별자는 다음이다. `rule_version_id`나 `monthly_plan_id`를 버킷의 유일키로 사용하지 않는다.

```sql
UNIQUE (family_id, child_id, stable_scope_id, business_date)
```

한도 소비와 효과 적용은 같은 트랜잭션에서 처리한다. 실제 동시 요청 방어에는 동일 버킷의 행 잠금과 유일키가 필요하다. `CHECK`로 다른 행 전체의 합계를 검사하려는 구조는 쓰지 않는다.[1]

호출 예시는 별도 부모 API 세션에서 다음과 같다. `request.jwt.claims`는 검증된 서버가 설정해야 하며 브라우저에서 부모 ID를 넣어 권한을 얻는 기능이 아니다.

```sql
SELECT pr_design.recognize_lifestyle_event(
  'fam-a', 'child-a', 'rv-l001',
  TIMESTAMPTZ '2026-10-17 10:00+09',
  'mobile-request-001',
  '{"action":"cat-litter","evidence":"parent-observed"}'::jsonb
);
```

같은 요청키 재전송과 같은 실제 사건은 새로운 인정·효과를 만들지 않아야 한다. 같은 키로 다른 규칙·시각·내용을 보내면 거절한다. 한 인정의 두 자산 효과는 한도 소비 한 건에 연결한다.

패널티는 기록 공란에서 자동 생성하지 않는다. L-013은 부모가 직접 확인한 실제 미복용 생활 사건으로 별도 보존하며, 아침·저녁 구조화 복약일지와 연결해 자동 차감하지 않는다. 점검 횟수와 차감 상한이 같은 뜻인지 미확정인 다른 규칙은 그 결정을 코드 기본값으로 넣지 않는다.

## 4. 학교 최고구간 총액과 권리·이행

| 확인된 학교 스티커 | 최종 목표 권리액 |
|---:|---:|
| 0~4개 | 쿠페이머니 0원 |
| 5~7개 | 쿠페이머니 10,000원 |
| 8개 이상 | 쿠페이머니 **총 15,000원** |
| 미확인·교사 피드백 누락 | 최종 마감 보류 |

학교의 기본 인정과 교사 칭찬은 출처를 별도로 저장하되 **학교 종류**의 주간 집계에 포함한다. Lifestyle이나 다른 학습 스티커는 합산하지 않는다. 문제 있는 날의 칭찬 처리 방식은 아직 미확정이므로 해당 조합은 보류한다.

```text
추가권리 = max(0, 목표총액 − 기존 유효 권리 순발행액)
아직 제공할 양 = max(0, 유효 권리액 − 실제 순이행액)
```

5개에 10,000원 권리가 발행되고 같은 주 합계가 8개가 되면 추가권리는 5,000원이다. 기존 10,000원이 아직 지급되지 않았다고 새 15,000원 권리를 발행하지 않는다. 같은 10,000원 권리와 실제 지급 10,000원이 함께 있어도 목표 15,000원의 추가분은 5,000원이다.

이행은 각 보상권의 미이행액을 넘지 않도록 해당 권리에 연결한다. 여러 권리 10,000원+5,000원을 한 번에 이행하더라도 첫 10,000원 권리에 15,000원을 기록하는 방식은 쓰지 않는다. 하향 정정으로 목표가 이미 발행·이행된 값보다 작아지면 검토 상태로 두고 자동 회수하지 않는다.

샘플 SQL은 기간의 끝을 제외한다. `2026-10-19~25`라는 화면 주간은 `[2026-10-19, 2026-10-26)`이다. 다음 월요일을 두 주에 함께 넣지 않는다. 월을 걸쳐도 기간 정본 한 개를 사용한다. **월요일 시작 및 일반 중간지급은 사용자 확정 정책이 아닌 검증 예시**다.

실행 가능한 부모 범위 목록·한도 조회·학교 계산·권리/이행 조회는 [samples.sql](database/samples.sql)에 있다. 일반 중간발행은 운영 기본으로 허용하지 않고 독립 시험 모드와 명시적 시험 결정에서만 비교한다.

## 5. 표 중심 프로토타입

| 상단 경로 | 화면에서 할 일 |
|---|---|
| `/operations` | 날짜·종류·미확인 필터, 실제 회차, 명시적 정상 일괄 확인 |
| `/operations?view=week` | 학교 기본/칭찬 별도 확인, 미확인 보류, 최고총액 차액 계산 |
| `/regulations` | 26개 시행규칙의 번호·기준·보상·미정 상태 조회 |
| `/rewards` | 발행 권리와 실제 이행·미이행 구분 |
| `/reinforcers` | 한 번 등록한 강화물 카탈로그 재사용 |
| `/settings` | 계정·보호자·복약 접근 경계 설명, 모의 CSV·초기화 |

화면은 모의 데이터를 브라우저에만 저장한다. 정상 PASS는 부모의 명시적 일괄 확인으로 줄이고 패널티·미정 관계는 그 일괄 처리에서 제외한다. 감사 기록을 사용자가 별도 입력하도록 요구하지 않는다.

표 머리글은 하나의 의미 있는 HTML 표 안에서 고정한다. 고정 헤더를 별도 표로 분리하지 않는 이유는 머리글과 데이터의 접근성 관계를 보존하기 위해서다.[2] 작은 화면에서는 페이지 전체가 아니라 표 영역만 가로 스크롤한다.

[프로토타입 실행법](prototype/README.md)을 참고한다. 새 WebDev 프로젝트 초기화가 이 세션에서 제한되어 별도 코드 패키지와 임시 미리보기 서버로 제공했다. 기존 서비스의 관리 페이지를 이 프로토타입으로 교체하지 않았다.

## 6. 재사용 스킬과 검증 경계

`family-rule-governance` 스킬은 사용자 원문 추출 → 확정/미정 분리 → 규정 계보·월별 채택 → 관계형 DB → 한도/최고총액 → 표 UI → 독립 검증·필요 시 실제 Grok 2차 검토의 절차를 담는다. 정책 예시와 검증 반례는 참조 파일, 순수 산술 확인은 별도 스크립트에 분리했다.

이번 SQL은 격리 PostgreSQL 엔진의 함수·FK·제약 시험이고, 프런트는 순수 계산·메뉴 동작·모의 지급 시험이다. 운영 Supabase의 실제 RLS/다중 연결 부하, 완전한 법령 게시 처리기, 실제 자정 정산 원장, 외부 송금·충전은 구현·검증 범위가 아니다. 기존 Grok 검토는 법령형 구조와 DB 확장성 검토의 근거이며 이번 신규 DDL 전체의 재검토 완료를 뜻하지 않는다.

## 최종 전달 검증

- 격리 설계: **38개 테이블**, 원문 시행규칙 **26개**. 모든 규칙은 정확한 세 하위규정 버전 중 해당 종류의 근거 버전을 연결한다. 조건별 효과는 정규화한 `rule_conditions` 키를 FK로 참조한다.
- SQL: PGlite **39개 검사 통과**. 실제 결과는 `database/verify-result.json`에 보존했다. 샘플 SQL 전체 실행은 `database/verify-samples.mjs`로 재현한다.
- 웹 코드: **23개 순수 회귀시험과 TypeScript·Vite 빌드 통과**. 실제 브라우저에서 4회/3회/45분, 미확인 학교 발행 보류, 10,000원+5,000원 권리, 15,000원 모의 이행 후 하향 정정 보류, 다섯 상단 메뉴의 URL 이동을 확인했다. 작은 iframe 뷰포트에서도 전체 페이지가 아니라 표 영역만 가로 스크롤했다.
- 재사용 스킬: 구조 검사와 별도 정책 산술 스크립트 실행 통과.

이 결과는 기존 앱의 실제 부모·자녀 연동이나 운영 원장 통합 완료를 뜻하지 않는다. 기존 운영 데이터는 변경하지 않았다.
