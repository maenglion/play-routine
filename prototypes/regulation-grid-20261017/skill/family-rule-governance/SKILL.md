# 가족 규정·관계형 DB·표 UI 설계

## 범위를 고정한다

**문서 정리 / 독립 설계·시험 / 실제 운영 배포**를 구분한다. SQL·프로토타입 요청을 기존 규칙 초기화·자동 차감·서비스 교체 승인으로 해석하지 않는다. 파일·기기·커넥터의 실제 접근 가능성을 확인한다.

Play Routine이면 `references/play-routine-policy.md`를 읽고 최신 기본법·하위규정·시행령·승계 문서를 함께 읽는다. 다른 서비스이면 동일한 구조로 사용자 원문을 정리한다. 이전 세션 경로만 보고 현재 파일이 있다고 가정하지 않는다.

## 1. 사실과 결정 경계를 추출한다

영구 번호·종류·목적과 반복 주기·업무 기간을 분리한다. Task/Quest/Lifestyle은 종류이고 일/주/월/사건은 주기다. 같은 교재의 일별 수행과 월간 성취를 서로 다른 인정 관계로 남긴다.

보상·명시 중립·무보상 미달·패널티 후보·부모 미확인·분류 잔차를 구별한다. 한 인정의 효과 1~2개, 독립 자산·단위, 인정 한도와 점검 횟수를 따로 추출한다. 두 번째 효과는 선택사항이다.

각 값을 원문·사용자 확정·예시 가정·미정으로 표시한다. 미정은 `NULL/pending`이며 0·없음·실패가 아니다. 이미 해결한 질문은 반복하지 않는다. 지급·차감·기간이 달라지는 충돌만 한 가지씩 확인한다. 재량형 생활 평가를 임의 세부 점수제로 바꾸지 않는다.

## 2. 규정 계보와 승계를 설계한다

상위 목적 → 기본규정 → 세 하위규정 → 공통 처리규율 → 개별 시행규칙 → 월별 버전 채택의 관계를 정의한다. 규정·규칙·강화물 정체성 ID와 불변 버전을 분리한다. 개정·폐지·승계 이벤트에 `effective_at`, `recorded_at`을 남긴다.

정확한 상위/하위/강화물/처리기 버전 조합을 채택한다. 다음 달은 규칙 복사가 아니라 기존 승인 버전 참조다. 상위 변경의 영향 목록을 검토한다. 규칙 종료로 계정·가족·카탈로그·사건·권리·이행·원장을 삭제하지 않는다. 과거 원장 정정은 조정 행으로 남긴다.

## 3. DB 책임을 층별로 분리한다

관계를 먼저 설명하고 DDL을 작성한다. 최소 층은 가족·멤버십, 규정·규칙 버전, 조건·효과, 월별 채택, 자산·강화물, 예정회차·원사건·부모 확인, 스티커·기간, 한도 사용, 보상권·실제 이행·원장, 잔차·민감 관찰이다.

가족별 복합 FK로 다른 가족의 자녀·규칙·강화물 연결을 차단한다. 읽기 권한과 부모 RPC 쓰기를 분리한다. 표 편집 UX를 raw table UPDATE 권한으로 구현하지 않는다. 호출자 ID를 클라이언트 인자로 받아 신뢰하지 않는다.

스티커 아이콘은 표시 자원이다. 종류·원천 규칙·자녀·회차·확인 revision이 계산 정체성이다. 부모 미확인·교사 피드백 누락에서 0개·위반·차감을 추정하지 않는다. 약물·양육일기는 상태 조회·보상 규칙과 분리한다.

## 4. 한도와 최고총액을 구현한다

한도 키는 가족·자녀·안정된 규칙 한도 범위·업무일/사건이다. 새 규칙 버전이나 월별 계획이 동일 기간 한도를 초기화하지 못하게 한다. 한 인정에서 효과 둘을 만들어도 카운트는 한 번 소비한다. 초과 원사건은 보존한다. 동일 요청키 재전송은 한 번만 실행하고 같은 키 다른 내용은 거절한다. UNIQUE·행/트랜잭션 잠금으로 보호한다.

최고구간 총액형과 누적 가산형을 별도 정책으로 둔다. 최고구간이면 다음을 사용한다.

```text
목표 권리총액 = 최고 충족 구간의 최종총액
추가권리 = max(0, 목표총액 - 기존 유효 순발행권리)
미이행액 = max(0, 유효 권리 - 실제 순이행)
```

미이행권리를 기존 권리에서 빼고 새권리를 발행하지 않는다. 하향 정정으로 발행/이행보다 목표가 작으면 검토 상태로 두고 자동 회수하지 않는다. 미확인 마감과 실제 지급 시점 규정을 점검한다. 월을 걸친 하나의 주간은 기간 정본 하나를 사용한다.

## 5. 부모 UI를 운영표와 경로로 단순화한다

상단 글자 메뉴를 **운영표 / 규정 / 보상·원장 / 강화물 / 설정·기록**으로 나눈다. URL로 화면·기간·필터를 복원한다. 표 머리글·첫 식별열을 고정하되 HTML 표를 둘로 쪼개지 않는다. 키보드 포커스·모바일 가로 스크롤을 제공한다.

부모 한 명 기준으로 선택 단계는 줄이되 DB를 단일 부모 ID로 고정하지 않는다. 통상 PASS는 부모의 명시적 일괄 확인과 선택 사유를 제공한다. 패널티·충돌·정정에는 근거를 요구한다. 감사·revision·요청키·소급은 시스템이 자동 기록한다.

강화물은 태그 카탈로그로 재사용한다. 계정·보호자·CSV 설정은 기본 접힘 또는 설정 메뉴로 이동한다. 자녀 화면은 자기 수행·미확인·확정 효과를 단순하게 표시한다.

프로토타입은 모의 데이터·별도 저장 키·초기화 범위를 표시한다. WebDev 도구를 먼저 사용한다. 별도 초기화가 실제 실패하면 운영 폴더를 지우지 말고 독립 코드 패키지로 제공하며 생성·게시 완료를 꾸며 쓰지 않는다.

## 6. 독립 검증·2차 검토를 수행한다

`references/verification-contract.md`의 반례를 입력·독립 기대값·중간 상태로 실행한다. SQL 파싱에 그치지 말고 격리 PostgreSQL에서 함수·FK·제약을 실행한다. 확인·권리·이행·정정 각 단계 값을 검사한다. PGlite 순차 검증을 실제 병렬 부하·Supabase RLS 시험으로 표시하지 않는다.

필요하거나 사용자 요청이 있으면 실제 Grok에 현재 문서/DDL·확정/미정표를 전달한다. 저장된 인증을 사용하고 모델·대상 버전·응답 완결을 보존한다. 검토 의견을 사용자 정책 승인으로 간주하지 않는다. 기존 검토를 재사용하면 당시 대상과 새 설계의 차이를 밝힌다.

UI 메뉴·미확인 보류·한도 초과·재전송·최고총액·CSV 수식 방지·모바일 폭·키보드 접근을 시험한다. 프런트 통과를 DB 동시성이나 실제 지급 검증으로 표현하지 않는다.

산술 기대값을 분리 확인할 때는 `scripts/check_policy_math.py --self-test`를 실행하거나 명시적 입력 JSON을 전달한다. 이 도구는 정책 산술만 계산하며 DB·동시성·지급 시험이 아니다.

## 출력·완료 기준

요청 범위에 맞는 완결 파일을 제공한다. 관계·확정/미정표·엔티티 사전·시행규칙 매핑, 독립 `schema.sql`/`seed.sql`/`samples.sql`/검증 결과, 표 프로토타입 소스·실행법을 같은 정책 계약으로 맞춘다. 실제 모델 검토 원문은 대상·완결 근거와 연결한다.

운영 미적용·미구현 정산/권한 경계를 해당 부분 옆에 명시한다. 파일을 절대 경로 링크로 전달하고 초보 사용자에게 다음 행동은 한 단계만 제시한다.
